# 本机显示验证

本入口属于 `validate-local-display-control` 阶段零，默认只读。两条显示控制路径须分别完成实机验收，才能进入后续产品实现。

## 构建与只读启动

在仓库根目录执行：

```sh
swift build
swift test
swift run extilume-probe
```

若托管执行环境拒绝 SwiftPM 的嵌套 `sandbox-exec`，可使用以下命令；工具自身的权限限制仍然生效：

```sh
CLANG_MODULE_CACHE_PATH=/private/tmp/extilume-clang-cache swift build --disable-sandbox --cache-path /private/tmp/extilume-swift-cache
CLANG_MODULE_CACHE_PATH=/private/tmp/extilume-clang-cache swift test --disable-sandbox --cache-path /private/tmp/extilume-swift-cache
CLANG_MODULE_CACHE_PATH=/private/tmp/extilume-clang-cache swift run --disable-sandbox --cache-path /private/tmp/extilume-swift-cache extilume-probe
```

托管沙箱可能令 CoreGraphics 返回空列表，程序会报告阻塞并返回非零退出码；不能把受限环境的空结果解释为没有显示器。用 `swift build --show-bin-path` 查询当前构建产物目录，不要假定 `.build/debug` 始终是实际产物。

程序读取系统版本、架构、开合盖状态和显示拓扑，报告使用内屏、外屏等标签。程序不打印显示器序列号、原始 UUID、数字 ID、窗口内容或个人路径。启动前后比较显示器集合、在线/活动/主屏/镜像状态、原点、尺寸、旋转及当前显示模式；这个有限观测不能证明所有设置未变，也不能证明后续控制与恢复有效。

只读命令输出后自行退出；运行期间可用 `Ctrl-C` 停止。它不修改显示布局、分辨率、亮度、启用位，也不启动保护进程。

## 主动验证与停止

主屏命令已实现但尚未完成实机验收。用户明确启动单项试验时，保持开盖、单台已确认物理 HDMI 外屏与双屏非镜像桌面。准备当前用户独有、权限为 `0700` 的状态目录：

```sh
mkdir -m 700 .extilume-verification-state
extilume_bin_dir="$(swift build --show-bin-path)"
"$extilume_bin_dir/extilume-probe" --verify-primary .extilume-verification-state
```

托管环境取得构建目录时也要带上前述 module cache、`--disable-sandbox` 与 `--cache-path` 参数。目录已存在时先检查归属、权限与未决责任，不删除已有记录来启动新试验。入口取得目录独占锁；有任何恢复记录即拒绝新会话。

启动先连续读回相同配置；开盖、物理 HDMI 与双屏扩展条件不满足时保留事件监听，等待条件就绪，不创建新事务。符合条件后原子保存恢复责任，使用公开原点事务与 `.forAppOnly` 将整个布局平移到外屏为主屏。仅监听 CoreGraphics 回调与唤醒事件时进行有限重读，不持续轮询。输入 `status` 查看活动屏、主屏与事务数；已经是目标布局时，重复事件不会产生新事务。自动连接／唤醒生命周期尚未验收，不应依赖其自动接管。

主屏运行与只读事件观察入口使用 AppKit 的完整事件循环，激活策略为 `prohibited`，不创建窗口或抢焦点。CoreGraphics 回调只负责将工作送入串行队列；裸 `CFRunLoopRun` 或仅初始化 AppKit 不能替代这两个入口的事件处理。恢复、终验和短进程读回仍是执行后退出的命令。

手动在系统设置修改布局后，输入 `confirm-user` 明确确认此次操作来自用户，再输入 `reapply` 验证 C → B。`confirm-user` 不应由脚本按延时自动发送；不同布局或回调本身不能证明是用户修改。来源未知时保留责任并拒绝重新接管。

为避免持续进程的陈旧读回被当作当前配置，控制器使用同用户短进程进行稳定读回，通过匿名 IPC 返回快照，在提交前后和恢复前后核对；短进程完成后有界回收。原始身份只在内存与该 IPC 内传递，不进入参数或日志。确认 C 时要求实际布局不同于应用 B；无法取得独立观测即停止操作、保留责任，不把旧读回当作确认成功。正常稳定期间不持续启动观测进程。

若原进程已经退出，记录仍处于 `owned`，且你确认当前不同于应用 B 的布局是手动修改的 C，可先运行 `--confirm-user-primary <同一状态目录>`，再进行补偿；该确认命令只更新来源与恢复基准，不写显示配置。提交中或恢复中的记录不能用此命令改成新基准。重连读回已知 A 可保留原基准并等待重新应用；陌生布局或此前未决来源仍须明确确认。

输入 `stop`、发送 EOF 或按 `Ctrl-C` 时，程序只提交负责的原点布局到 `.forSession`，不写永久配置。正常停止后，责任记录保留到另一进程读回基准一致：

```sh
"$extilume_bin_dir/extilume-probe"
"$extilume_bin_dir/extilume-probe" --finalize-primary .extilume-verification-state
```

异常退出后的补偿命令为：

```sh
"$extilume_bin_dir/extilume-probe" --recover-primary .extilume-verification-state
"$extilume_bin_dir/extilume-probe" --finalize-primary .extilume-verification-state
```

缺失身份、布局来源未知或恢复读回不符会保留责任并返回失败。不要输出或手动删除状态文件：其中含稳定显示身份，仅供当前用户恢复读取。该命令不处理内屏启用责任。当前辅助进程仅支持下面的无显示写入演练；真实内屏停用尚未实现，不能启动对应验证。

主屏试验的停止条件是：主进程退出后，由独立观测确认最新用户配置 C 保留，且没有未决恢复责任。内屏停用试验还要求先读回内屏可用及适用配置恢复，再清理保护进程；恢复未完成不能仅靠结束进程收束。只读入口不创建控制事务，退出无需恢复。

### 主屏逐场景复现与判定

以下是验收方法，不是所有场景已通过的声明。主动场景只在用户明确启动、开盖与安全拓扑满足时执行；拔插和睡眠须另行安排，不由这张表自动触发。每项记录系统、连接链路、代码版本、输入、独立读回及未决责任；详细结果留在本地 `.local/verification/`。

| 场景 | 复现方法 | 判定依据 |
| --- | --- | --- |
| 开盖启动 A → B | 记录只读 A，运行 `--verify-primary`，独立读回 B，人工确认两屏桌面 | HDMI 主屏、内屏保留扩展桌面，相对位置不变 |
| 重复接管 | 在 B 上重复输入 `reapply`，再输入 `status` | 不增加事务数或代次；独立布局仍是 B |
| 正常退出 | 输入 `stop`，等待进程退出，独立只读及 `--finalize-primary` | 最终 A 一致；清除发生在退出后终验成功时 |
| 用户 C → B → 退出 | 手动修改主屏与位置，刷新率保持用户原选项；确认 `confirm-user` 后 `reapply`、`stop` | 独立终验保留最新 C 和刷新率，不恢复旧 A |
| 用户 C 后直接退出 | 手动修改 C 并明确 `confirm-user`，不重新应用，输入 `stop` | 退出后 C 与未控制设置保持一致 |
| 主进程强退及退出后重连 | 只强退本轮控制主进程；独立读回，再按现场安排拔插，最后补偿和终验 | 分别记录退出后与重连后的布局；不能据此证明存活期间自动重连 |
| 合盖启动与退出 | 保持合盖及可用外屏，启动控制器，分别验证 `stop`、EOF、`SIGTERM` | 只等待，事务数为 0；退出成功且无新增恢复记录，不证明开盖内屏停用 |
| 启动时缺外屏、运行中插入 | 现场确认内屏桌面可用，再分别从缺外屏状态启动、接入外屏 | 缺外屏时不控制；稳定且符合范围后自动接管，基准不得取旧 B |
| 存活期间断开与重连 | 控制器运行期间进行已安排的拔插，逐步独立读回 | 缺屏只处理适用责任且不清除完整责任；重连不把 B 保存为原状 |
| 睡眠唤醒及唤醒后 C 恢复 | 记录 C，按现场安排睡眠唤醒，核对稳定后接管与退出 | 自动接管恢复到最新 C，未控制设置保留；缺少实测则为未验证 |
| 物理事件观察 | 单独运行 `--watch-connection`，同时留存现场动作及独立读回 | 初次 `matched` 与人工 `mark` 不算物理事件；对照程序回调不能替代修复入口全链路验证 |

失败轮次保留失败结论和收束结果，修复后的通过记录单列。未执行的场景写明“未验证”，不能由构建、自检或其他场景的通过推定。主屏完整生命周期未通过时不允许阶段一准入。

### 当前主屏验收结论

已执行的生命周期验收适用于本机 Apple Silicon MacBook Pro、macOS 27.0.1 (26A434)、Mac USB-C → 型号未知 Hub → HDMI、一台物理外屏、开盖且非镜像。验收使用当前工作树构建；更换系统、链路或影响控制／恢复的代码后，不能直接继承结论。

| 验收项 | 当前结论 |
| --- | --- |
| 无外屏启动、接入后自动接管 | 通过；缺屏等待不创建事务，接入后外屏成为主屏 |
| 已连接启动、重复接管 | 通过；内屏保留扩展桌面，重复输入不增加事务或代次 |
| 用户 C → 再接管 → 正常退出 | 通过；手动修改不立即抢回，独立终验恢复最新 C |
| 运行中断开、缺失责任、自动重连 | 通过；缺屏时完整责任保留，重连未把应用 B 保存为原状，正常退出恢复 C |
| 用户 C → 睡眠／唤醒自动接管 → 退出 | 通过；无需手动 reapply，正常退出后独立恢复睡前 C |
| 当前 Hub 链路 C 后直接退出、主进程强退及退出后重连 | 未验证；旧 Mac HDMI 直连结果单独保留，不替代本链路证据 |
| 阶段一准入 | 暂未放行；需补齐同一验收链路的上述缺项 |
| 阶段二准入 | 阻断；真实内屏停用、及时物理断开、全过程异常恢复和逐次 10 秒时限未验收 |

接入与重连阶段曾出现暂态拓扑变化及再次接管，具体原因未确认；这些结果不证明任意事件交错只产生单事务。详细逐场景证据与旧失败轮次保留在忽略目录 `.local/verification/`，不进入 Git。最近睡眠轮已正常退出、独立恢复 C，并在用户本轮条件授权下经原生终验清除恢复记录；收束时目标进程为 0、无未决责任。更换连接后的当前布局需另行读取。

控制与恢复只写原点，不设置或回写刷新率、显示模式、分辨率或旋转。内屏 120、外屏 30 是该轮 `CGDisplayMode.refreshRate` 的读回值，不是实时面板刷新率；系统设置是否选择 ProMotion 未单独读回，不能据此宣称该选项已验收。复现时保持用户原刷新率选项。

## 不改显示设置的保护演练

保持桌面唤醒，使用同一空的 `0700` 状态目录：

```sh
"$extilume_bin_dir/extilume-probe" --guard-drill .extilume-verification-state
```

演练记录当前布局，目标等于基准，不调用原点或启用位写 API。它用 `posix_spawn` 启动同用户独立辅助进程，通过匿名 socket 传递会话、代次与父进程身份。辅助进程验证受限记录、注册父进程退出事件后回复就绪。授权自检拒绝未就绪、错误合同、旧代次及失效后重握手；新握手验证失败会立即撤销旧就绪授权。演练期间不得搬移或替换状态目录。

- `status`：核对保护仍就绪；稳定期间采用进程与 IPC 事件等待，不定期读取显示列表。
- `stop`：主进程核验基准、保存恢复状态，通知辅助进程停止新接管。辅助进程继续等到主进程实际退出，再独立读回，退出后记录仍保留。
- `crash`：只让演练主进程异常退出；辅助进程取得原目录独占锁，重读最新同会话记录并核验实际基准，保存恢复结果后退出。
- `lose-guard`：只终止本演练启动的辅助进程；主进程撤销授权，核验并退出，不继续控制。

每轮等待辅助进程退出后独立核验成功，确认无本轮进程，再执行 `--finalize-primary` 独立终验并清除记录。主进程仍活着时，不把辅助进程收到停止通知当作已退出。若核验不符，保留记录与保护；先恢复桌面可读状态，不删除记录启动新会话。握手失败时禁止控制；对无配置写入的演练记录，`--recover-primary` 可进行只读核验补偿。

日志的“通知至核验”仅是进程事件通知后的耗时，不能作为实际故障至恢复的 10 秒验收证据。`RecoveryTiming` 的离线自检使用实际故障、通知和恢复三个同源时间戳，延迟通知计入总时长；原生时基为包含睡眠的 `mach_continuous_time`。物理拔线起点、误差与真实内屏可用恢复仍未测量。

演练尚未接入物理设备事件与真实内屏启用恢复；未决演练按退避重试并保留进程。这些限制须在真实停用前处理。演练通过不能替代全过程故障交错或开盖停用实测。

完整演练可运行：

```sh
python3 scripts/verify-guard-drill.py "$extilume_bin_dir/extilume-probe"
```

脚本依次运行 `stop`、`crash`、`lose-guard`，核对同用户父子关系、稳定保护、第二实例与提前终验拒绝、退出后责任状态及独立清理。它仅结束自己创建的演练进程；失败保留该轮受限目录与记录，不自动删除未决责任。

保护协议交错检查同样无需拔插或显示写入：

```sh
python3 scripts/verify-guard-interleavings.py "$extilume_bin_dir/extilume-probe"
```

该脚本通过匿名 IPC 读取当前布局，建立目标等于基准、无内屏责任的 `applying` 记录；当前用户独有的临时目录和记录分别为 `0700`、`0600`。五个场景覆盖父进程存活时的 IPC EOF、停止接管通知、辅助进程就绪前终止、旧代次记录拒绝，以及父进程退出后重读最新代次。父进程持锁期间独立恢复必须被拒绝；父退出后的核验、辅助进程实际退出与独立终验成功后才清理目录。失败保留责任，不杀其他任务进程。协议帧使用一个覆盖头部和负载的总 deadline；演练失败后脚本有界等待自己终止的父进程退出。

这里的父进程为 Python 协议驱动器，不能替代原生控制器在真实停用、提交中和恢复中的全过程交错。无写入记录的补偿先校验当前布局等于基准；不符即拒绝并保留责任。检查通过不证明真实内屏恢复或实际故障至恢复的 10 秒标准。

## 范围与证据

### 只读物理事件观察

桌面唤醒、HDMI 已接入且唯一物理身份已确认时运行：

```sh
"$extilume_bin_dir/extilume-probe" --watch-connection
```

观察入口精确匹配当前 HDMI 的 IOKit service，仅输出目标服务的 interest、property-change、匹配／终止事件及 CG 回调的相对单调毫秒，不输出设备路径或身份。输入 `mark` 是人工准备标记，不是实际拔线时刻；`stop` 释放监听并退出。CG 回调附带的进程内活动数只用于查找陈旧读回，不证明物理外屏可用。

IOKit 通用 SDK 声明不保证这条 HDMI 链路在拔线时产生 property-change 或 service termination，必须与实际拔线及新进程读回对应。没有目标设备事件或无法约束通知延迟时不能据此授权停用；人工标记至事件的间隔也不能冒充实际断开检测延迟。此入口不执行任何配置写入、不创建恢复记录。

范围判断必须拒绝镜像、多外屏、虚拟屏和无法确认物理身份的外屏。非内置、在线或主屏属性均不足以单独证明物理 HDMI 连接。

本机 HDMI 匹配在进程内精确比较 CoreDisplay 提供的设备位置与 IOKit 的注册路径；仅当匹配唯一、下游为 HDMI、EDID 身份非空且系统 UUID 可解析时才确认物理外屏。CoreDisplay 只读符号通过动态加载获取，私有符号或字段缺失即保持未知，不采用打分猜测。UUID 和设备路径不打印、不由只读入口落盘。此路径只验证本轮系统和 HDMI 链路，不扩大到其他连接方式。

## 恢复数据与来源

恢复模型只包含会话、事务代次、阶段、稳定显示身份、主屏和所有相关原点组成的布局组，以及单独的内屏启用位。分辨率、刷新率、旋转、亮度、颜色、窗口和 Spaces 不属于恢复负载，不能从旧快照回写。

- 初次 A → B 保留 A；已经确认的用户 C 在再次接管前成为新基准，C → B 之后恢复 C。
- 用户 C 后直接退出，未被重新接管的布局不生成回写计划。
- 自身回调和重连残留 B 保留原基准；提交或恢复期间的读回不能被提升为用户配置。
- 用户 C 已解除当前责任后，若完整读回再次出现已知应用 B，恢复责任重新标记，基准仍为 C；此前未决来源不会因此被清除。
- `confirmedUser` 表示调用方已有用户操作证据，不能仅凭等待结束或出现不同布局来传入该来源。来源未知时保留责任、停止新接管；运行时事件如何取得这个证据仍属于后续控制集成与实机验收。
- 恢复前重新映射稳定身份到当前数字 ID，同时读当前布局；数字 ID 重用、身份冲突、零 ID、无证据的 C 或无关屏均拒绝布局回写。
- 原主屏缺失时只计算适用部分的平移，缺失布局组责任保留；部分恢复读回不能清除完整布局责任。内屏启用位独立于布局来源，未恢复的启用责任仍提供安全恢复计划。

恢复成功须读回基准布局，以及记录中存在的内屏启用位；即使该启用位已无 pending 标记，也不能省略实际核验。当前主屏终验命令拒绝含内屏启用责任的记录，不替尚未实现的停用路径清除责任。

`RecoveryStore.apply` 的自检确认 prepared、applying 已落盘后才允许控制回调运行，回调失败保留责任；目录须当前用户所有且为 `0700`，记录为 `0600`，拒绝符号链接、非普通文件、损坏负载与放宽权限。未完成事务不可清除。原点控制入口已接入该守卫；真实文件系统写入失败、并发保护进程、系统回调来源交错和恢复后的实际桌面仍需后续任务逐项验证。

存储层要求同一实例先成功取得目录独占锁，才能调用 `save`、`clear` 或 `apply`；未持锁或取得锁失败时返回 `ownershipUnavailable`，不创建记录、不执行控制回调，也不能覆盖或清除另一实例的责任。`load` 仍允许保护进程在就绪握手前只读查看责任。实例由调用方串行访问；释放实例时关闭目录句柄并释放锁，接任者须重新取得锁并读回记录。

缺屏期间的被动观察保留完整基准；缺失布局不能被人工确认成完整 C，出现记录之外的显示身份也会转为未决来源。无写入保护演练与辅助进程通过独立短进程核对当前布局，避免长期进程缓存被当作退出后的恢复证据。

就绪读取及恢复模型的自动检查无需拔插：

```sh
swift test
python3 scripts/test_verify_guard_drill.py
```

保护演练脚本以同一个单调 deadline 等待完整就绪行，不预读后续消息；半行、EOF、非就绪首行或超过 4096 字节的首行均拒绝。
