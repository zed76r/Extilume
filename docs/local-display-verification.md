# 本机显示验证

本入口属于 `validate-local-display-control` 阶段零，默认只读。两条显示控制路径须分别完成实机验收，才能进入后续产品实现。

## 构建与只读启动

在仓库根目录执行：

```sh
swift build
swift test
swift run extilume-probe
```

若托管执行环境拒绝 SwiftPM 的嵌套 `sandbox-exec`，可使用以下命令；工具自身的权限限制仍然生效：

```sh
CLANG_MODULE_CACHE_PATH=/private/tmp/extilume-clang-cache swift build --disable-sandbox --cache-path /private/tmp/extilume-swift-cache
CLANG_MODULE_CACHE_PATH=/private/tmp/extilume-clang-cache swift test --disable-sandbox --cache-path /private/tmp/extilume-swift-cache
CLANG_MODULE_CACHE_PATH=/private/tmp/extilume-clang-cache swift run --disable-sandbox --cache-path /private/tmp/extilume-swift-cache extilume-probe
```

托管沙箱可能令 CoreGraphics 返回空列表，程序会报告阻塞并返回非零退出码；不能把受限环境的空结果解释为没有显示器。用 `swift build --show-bin-path` 查询当前构建产物目录，不要假定 `.build/debug` 始终是实际产物。

程序读取系统版本、架构、开合盖状态和显示拓扑，报告使用内屏、外屏等标签。程序不打印显示器序列号、原始 UUID、数字 ID、窗口内容或个人路径。启动前后比较显示器集合、在线/活动/主屏/镜像状态、原点、尺寸、旋转及当前显示模式；这个有限观测不能证明所有设置未变，也不能证明后续控制与恢复有效。

只读命令输出后自行退出；运行期间可用 `Ctrl-C` 停止。它不修改显示布局、分辨率、亮度、启用位，也不启动保护进程。

## 主动验证与停止

主屏命令已实现但尚未完成实机验收。用户明确启动单项试验时，保持开盖、单台已确认物理 HDMI 外屏与双屏非镜像桌面。准备当前用户独有、权限为 `0700` 的状态目录：

```sh
mkdir -m 700 .extilume-verification-state
extilume_bin_dir="$(swift build --show-bin-path)"
"$extilume_bin_dir/extilume-probe" --verify-primary .extilume-verification-state
```

托管环境取得构建目录时也要带上前述 module cache、`--disable-sandbox` 与 `--cache-path` 参数。目录已存在时先检查归属、权限与未决责任，不删除已有记录来启动新试验。入口取得目录独占锁；有任何恢复记录即拒绝新会话。

启动先连续读回相同配置；开盖、物理 HDMI 与双屏扩展条件不满足时保留事件监听，等待条件就绪，不创建新事务。符合条件后原子保存恢复责任，使用公开原点事务与 `.forAppOnly` 将整个布局平移到外屏为主屏。仅监听 CoreGraphics 回调与唤醒事件时进行有限重读，不持续轮询。输入 `status` 查看活动屏、主屏与事务数；已经是目标布局时，重复事件不会产生新事务。自动连接／唤醒生命周期尚未验收，不应依赖其自动接管。

主屏运行与只读事件观察入口使用 AppKit 的完整事件循环，激活策略为 `prohibited`，不创建窗口或抢焦点。CoreGraphics 回调只负责将工作送入串行队列；裸 `CFRunLoopRun` 或仅初始化 AppKit 不能替代这两个入口的事件处理。恢复、终验和短进程读回仍是执行后退出的命令。

手动在系统设置修改布局后，输入 `confirm-user` 明确确认此次操作来自用户，再输入 `reapply` 验证 C → B。`confirm-user` 不应由脚本按延时自动发送；不同布局或回调本身不能证明是用户修改。来源未知时保留责任并拒绝重新接管。

为避免持续进程的陈旧读回被当作当前配置，控制器使用同用户短进程进行稳定读回，通过匿名 IPC 返回快照，在提交前后和恢复前后核对；短进程完成后有界回收。原始身份只在内存与该 IPC 内传递，不进入参数或日志。确认 C 时要求实际布局不同于应用 B；无法取得独立观测即停止操作、保留责任，不把旧读回当作确认成功。正常稳定期间不持续启动观测进程。

连接与唤醒先等待 1 秒再观察及尝试接管，连续连接事件和等待期间仅含桌面形状变化的事件重新计时，避免立即把暂态双屏布局写成未决来源。断开立即观察；开始配置、其他设置事件、明确确认 C、手动重新接管或退出均取消待执行接管。系统回调还会立即撤销已经开始读回的接管意图，观察结束和坐标写入前再次检查，避免串行队列被读回阻塞时遗漏已到达的用户事件。等待时间不证明来源或硬件已经稳定，提交前的完整快照相等检查与提交后目标读回仍不可省略。事务失败会输出责任落盘、写入前读回、坐标写入、目标读回或应用确认落盘的阶段标签，不输出设备身份。

写入前的独立读回与取消检查属于无显示副作用的预检。预检失败且操作尚未调用时，记录持久化回可重试的 `owned`：旧 `owned` 的基准、已应用布局、内屏及来源标记均保留，代次维持本次更高值；即使用户 C 已使 pending 为 false，也保留旧应用布局以供退出补偿。没有旧 `owned` 时，已应用值回到基准、pending 为 false，记录仍保留待恢复与终验。取消状态保存失败、操作已经开始后失败或进程在 `applying` 落盘后直接死亡，仍保留磁盘上的未完成阶段，不能据此重试或清除责任。取消不确认陌生布局为用户 C。

若原进程已经退出，记录仍处于 `owned`，且你确认当前不同于应用 B 的布局是手动修改的 C，可先运行 `--confirm-user-primary <同一状态目录>`，再进行补偿；该确认命令只更新来源与恢复基准，不写显示配置。提交中或恢复中的记录不能用此命令改成新基准。重连读回已知 A 可保留原基准并等待重新应用；陌生布局或此前未决来源仍须明确确认。

输入 `stop`、发送 EOF 或按 `Ctrl-C` 时，程序只提交负责的原点布局到 `.forSession`，不写永久配置。正常停止后，责任记录保留到另一进程读回基准一致：

```sh
"$extilume_bin_dir/extilume-probe"
"$extilume_bin_dir/extilume-probe" --finalize-primary .extilume-verification-state
```

异常退出后的补偿命令为：

```sh
"$extilume_bin_dir/extilume-probe" --recover-primary .extilume-verification-state
"$extilume_bin_dir/extilume-probe" --finalize-primary .extilume-verification-state
```

来源未决的记录只有在没有内屏启用责任、两个独立短进程均读回完整保存基准时，`--recover-primary` 才可只确认已恢复，不写显示配置、不更改基准、会话或代次；记录仍保留到独立终验。此分支仅供原控制进程退出后使用，运行中的正常停止仍须显式提交当前 C，防止 `.forAppOnly` 的退出回退覆盖用户配置。合盖缺屏、主屏或原点不同、读回失败均返回失败并原样保留记录。可用下列无显示写入 fixture 自检该边界（只有双屏时才增加 pending 布局与同身份原点不同的原生案例，单屏会明确跳过）：

```sh
python3 scripts/verify-primary-reconciliation.py "$extilume_bin_dir/extilume-probe"
```

其他缺失身份、布局来源未知或恢复读回不符仍会保留责任并返回失败。不要输出或手动删除状态文件：其中含稳定显示身份，仅供当前用户恢复读取。该命令不处理内屏启用责任。当前辅助进程仅支持下面的无显示写入演练；真实内屏停用尚未实现，不能启动对应验证。

主屏试验的停止条件是：主进程退出后，由独立观测确认最新用户配置 C 保留，且没有未决恢复责任。内屏停用试验还要求先读回内屏可用及适用配置恢复，再清理保护进程；恢复未完成不能仅靠结束进程收束。只读入口不创建控制事务，退出无需恢复。

### 主屏逐场景复现与判定

以下是验收方法，不是所有场景已通过的声明。主动场景只在用户明确启动、开盖与安全拓扑满足时执行；拔插和睡眠须另行安排，不由这张表自动触发。每项记录系统、连接链路、代码版本、输入、独立读回及未决责任；详细结果留在本地 `.local/verification/`。

| 场景 | 复现方法 | 判定依据 |
| --- | --- | --- |
| 开盖启动 A → B | 记录只读 A，运行 `--verify-primary`，独立读回 B，人工确认两屏桌面 | HDMI 主屏、内屏保留扩展桌面，相对位置不变 |
| 重复接管 | 在 B 上重复输入 `reapply`，再输入 `status` | 不增加事务数或代次；独立布局仍是 B |
| 正常退出 | 输入 `stop`，等待进程退出，独立只读及 `--finalize-primary` | 最终 A 一致；清除发生在退出后终验成功时 |
| 用户 C → B → 退出 | 手动修改主屏与位置，刷新率保持用户原选项；确认 `confirm-user` 后 `reapply`、`stop` | 独立终验保留最新 C 和刷新率，不恢复旧 A |
| 用户 C 后直接退出 | 手动修改 C 并明确 `confirm-user`，不重新应用，输入 `stop` | 退出后 C 与未控制设置保持一致 |
| 主进程强退及退出后重连 | 只强退本轮控制主进程；独立读回，再按现场安排拔插，最后补偿和终验 | 分别记录退出后与重连后的布局；不能据此证明存活期间自动重连 |
| 合盖启动与退出 | 保持合盖及可用外屏，启动控制器，分别验证 `stop`、EOF、`SIGTERM` | 只等待，事务数为 0；退出成功且无新增恢复记录，不证明开盖内屏停用 |
| 启动时缺外屏、运行中插入 | 现场确认内屏桌面可用，再分别从缺外屏状态启动、接入外屏 | 缺外屏时不控制；稳定且符合范围后自动接管，基准不得取旧 B |
| 存活期间断开与重连 | 控制器运行期间进行已安排的拔插，逐步独立读回 | 缺屏只处理适用责任且不清除完整责任；重连不把 B 保存为原状 |
| 睡眠唤醒及唤醒后 C 恢复 | 记录 C，按现场安排睡眠唤醒，核对稳定后接管与退出 | 自动接管恢复到最新 C，未控制设置保留；缺少实测则为未验证 |
| 物理事件观察 | 单独运行 `--watch-connection`，同时留存现场动作及独立读回 | 初次 `matched` 与人工 `mark` 不算物理事件；对照程序回调不能替代修复入口全链路验证 |

失败轮次保留失败结论和收束结果，修复后的通过记录单列。未执行的场景写明“未验证”，不能由构建、自检或其他场景的通过推定。主屏完整生命周期未通过时不允许阶段一准入。

### 当前主屏验收结论

已执行的生命周期验收适用于本机 Apple Silicon MacBook Pro、macOS 27.0.1 (26A434)、Mac USB-C → 型号未知 Hub → HDMI、一台物理外屏、开盖且非镜像。验收使用当前工作树构建；更换系统、链路或影响控制／恢复的代码后，不能直接继承结论。

| 验收项 | 当前结论 |
| --- | --- |
| 无外屏启动、接入后自动接管 | 通过；缺屏等待不创建事务，接入后外屏成为主屏 |
| 已连接启动、重复接管 | 通过；内屏保留扩展桌面，重复输入不增加事务或代次 |
| 用户 C → 再接管 → 正常退出 | 通过；手动修改不立即抢回，独立终验恢复最新 C |
| 运行中断开、缺失责任、自动重连 | 通过；缺屏时完整责任保留，重连未把应用 B 保存为原状，正常退出恢复 C |
| 用户 C → 睡眠／唤醒自动接管 → 退出 | 通过；无需手动 reapply，正常退出后独立恢复睡前 C |
| 当前 Hub 链路 C 后直接退出、主进程强退及退出后重连 | 未验证；旧 Mac HDMI 直连结果单独保留，不替代本链路证据 |
| 阶段一准入 | 暂未放行；需补齐同一验收链路的上述缺项 |
| 阶段二准入 | 阻断；真实内屏停用、及时物理断开、全过程异常恢复和逐次 10 秒时限未验收 |

接入与重连阶段曾出现暂态拓扑变化及再次接管，具体原因未确认；这些结果不证明任意事件交错只产生单事务。详细逐场景证据与旧失败轮次保留在忽略目录 `.local/verification/`，不进入 Git。最近睡眠轮已正常退出、独立恢复 C，并在用户本轮条件授权下经原生终验清除恢复记录；收束时目标进程为 0、无未决责任。更换连接后的当前布局需另行读取。

控制与恢复只写原点，不设置或回写刷新率、显示模式、分辨率或旋转。内屏 120、外屏 30 是该轮 `CGDisplayMode.refreshRate` 的读回值，不是实时面板刷新率；Hub 轮次未单独读回系统设置是否选择 ProMotion，不能据此宣称该轮选项已验收。直连补验的 UI 证据另列如下。复现时保持用户原刷新率选项。

当前 Mac HDMI 直连的补验结果独立于 Hub：

| 直连补验项 | 结论与边界 |
| --- | --- |
| 用户 C 后直接退出 | 通过；按授权经 Computer Use 只改主屏／排列，独立确认 C 后直接退出，终验保留 C 并清记录；UI 内屏 ProMotion、外屏“30 赫兹”选项前后保持 |
| 主进程强退后最终 C | 通过；只结束本轮验证主进程，退出后独立读回 C，显式补偿结束后再次核验、终验清记录；该轮 UI 内屏 ProMotion、外屏“可变（48–144 赫兹）”保持 |
| 用户 C → 睡眠／唤醒自动接管 → 退出 | 通过；睡前 C 由授权的界面操作设置，用户实际睡眠／唤醒后自动接管，无手动 reapply；正常退出后独立恢复最新 C，UI 原 ProMotion 与可变刷新率选项保持 |
| 当前直连运行中断开／重连 | 2026-10-14 修复版单轮读回通过；用户只拔插一次，缺屏时内屏为唯一活动主屏，完整 C 责任保留；插回后自动切至 HDMI 主屏，事务数 1→2，记录为 `owned`、代次 2、来源未决为 false；正常退出后独立恢复 C 并终验清记录。此前失败轮次仍保留 |
| 当前直连强退后再次连接 | 2026-10-14 修复版单轮读回通过；仅对本轮已核验 PID 的主进程发送 SIGKILL，退出后、用户单次拔插接回后、显式补偿退出后均独立读回 C；强退及拔插期间责任记录原样保留，补偿未改变基准、会话或代次，最后终验清记录且进程为 0 |
| 当前直连主屏路径准入 | 通过本轮原型准入；已有启动、重复接管、用户 C 直接退出／再接管恢复、睡眠唤醒证据，运行中重连及强退后再次连接缺口已由上述修复版实测补齐。允许进入阶段一菜单栏实现，完整应用仍需单独集成验收 |

前三轮均经独立终验收束；最近的直连重连失败轮退出控制器和观察器后，桌面读回 C，但当时责任仍未决，记录必须保留，后续主动控制前先处理。内屏始终保留活动桌面。这些证据不追溯覆盖 Hub 轮次，也不证明真实内屏恢复或故障至恢复的 10 秒时限。每轮保留开始时的用户刷新率选项，不把前一轮的选项当作恢复目标。

后续开盖后，两次独立读回均与该未决记录的完整基准一致，记录经不写显示配置的恢复确认、退出后独立核对及原生终验收束。2026-10-14 在开盖、Mac HDMI 直连条件下，使用包含写入前取消修复的新构建完成一轮拔插与正常退出复验：退出后内屏主屏原点 `(0,0)`、外屏右上原点 `(1728,-229)`；完整身份对应的恢复基准未改变，原生终验成功且本轮进程为 0、无遗留记录。详细证据保存在忽略的本地目录。

本轮接入期间观察到活动屏数暂态 2→1→2，最终自动接管成功；没有观测到实际写入前取消分支，不能用这一轮证明该分支在实机已触发。显示模式 getter 前后为内屏 120、外屏 144 Hz，仅证明有限读回一致，未重新核对系统设置选项或实时面板刷新率。只读监听器记录到 CoreGraphics 回调，未记录到目标 IOKit 设备事件；观察器时间戳不是实际拔线时刻，不能证明及时物理断开或 10 秒恢复时限。本轮始终保留内屏活动桌面，不构成真实内屏停用验收。

强退后重连补验使用同一 Mac、系统与 HDMI 直连链路、同一修复构建。主进程强退后的公开事务回退使桌面回到 C；接回后未运行新控制器，桌面仍为内屏主屏 `(0,0)`、外屏右上 `(1728,-229)`，与保存的完整基准一致。随后执行 `--recover-primary`、退出后独立读回与 `--finalize-primary`，责任结清。显示模式 getter 全程读回为内屏 120、外屏 144 Hz，没有写刷新率设置。此结果证明该轮强退后重连没有残留应用布局，不证明强退后仍有自动控制进程或真实内屏异常恢复。

阶段一准入结论仅适用于当前本机、已核验的物理 HDMI 直连及非镜像范围；来源未决仍须停止新接管、保留责任。内屏停用、及时物理设备事件、故障至恢复完整计时和全过程独立保护尚未验收，阶段二继续阻断，不影响主屏阶段一的独立准入。系统或链路变化后重新核对受影响证据。

## 不改显示设置的保护演练

私有启用位事务已实现隔离层，ABI 参考 [displayplacer 的声明](https://github.com/jakehilborn/displayplacer/blob/master/src/Header.h)。默认只读探测只解析 `CGSConfigureDisplayEnabled`，不调用该符号。事务在开始和提交前检查授权；配置失败或提交前撤权取消未提交事务，Complete 返回后不复用句柄。停用限定 `.forAppOnly`，恢复启用限定 `.forSession`，不设置显示模式或永久配置。真实停用入口仍未开放。

`disableInternal` 要求已落盘的同一条 `applying` 责任、启用基准、开盖、严格双屏拓扑、外屏主屏及稳定的身份和数字 ID，快照前后再次核对记录和保护。握手现在绑定会话、代次、父进程及可选内屏身份：普通演练的 nil 身份合同不能授权带内屏责任的事务，身份范围不同的 ready 也不能恢复授权。`checkProtection` 仍须核验辅助进程存活及恢复能力。

辅助进程在内屏合同就绪前解析启用符号，独立核对拓扑和活动内屏，并在发送 ready 前重读责任。父进程实际退出后，它取得目录独占锁，再读取最新同范围责任；需要时先启用内屏并独立读回，再按已有责任计算适用布局，只写原点。外屏缺失或布局来源未决不阻止安全启用，但会保留未完成的布局责任；完整布局和内屏状态均确认后才保存 `restored`，不自行清除记录。已恢复记录只核验，不重复写入。

当前验证结果：198 项 Swift、17 项 Python 测试、普通合同与内屏合同各 5 种原生无写入演练、11 组原有协议交错通过。假调用覆盖提交前拒绝、撤权、身份及代次变化、启用失败、先启用后布局、缺失外屏与未决来源；原生内屏合同演练始终令启用位基准和目标均为 true，没有调用真实启停。它们不证明真实回调跨线程时序、真实停用效果或 10 秒恢复。停用后内屏是否仍能枚举并读取 UUID／模式尚未实测；无法独立识别时当前恢复会失败并保留责任。5.1 和阶段二仍未完成。

保持桌面唤醒，使用同一空的 `0700` 状态目录：

```sh
"$extilume_bin_dir/extilume-probe" --guard-drill .extilume-verification-state
```

内屏合同接线使用 `--guard-drill-internal` 和另一个空的 `0700` 目录，要求开盖、外屏主屏及严格双屏范围。它记录的内屏基准与目标均为启用，不创建停用责任；其已恢复记录保留供复核，不能使用仅支持主屏责任的 `--finalize-primary` 清除。

演练记录当前布局，目标等于基准，不调用原点或启用位写 API。它用 `posix_spawn` 启动同用户独立辅助进程，通过匿名 socket 传递会话、代次与父进程身份。辅助进程验证受限记录、注册父进程退出事件后回复就绪。授权自检拒绝未就绪、错误合同、旧代次及失效后重握手；新握手验证失败会立即撤销旧就绪授权。演练期间不得搬移或替换状态目录。

- `status`：核对保护仍就绪；稳定期间采用进程与 IPC 事件等待，不定期读取显示列表。
- `stop`：主进程核验基准、保存恢复状态，通知辅助进程停止新接管。辅助进程继续等到主进程实际退出，再独立读回，退出后记录仍保留。
- `crash`：只让演练主进程异常退出；辅助进程取得原目录独占锁，重读最新同会话记录并核验实际基准，保存恢复结果后退出。
- `lose-guard`：只终止本演练启动的辅助进程；主进程撤销授权，核验并退出，不继续控制。
- `invalidate-connection`：注入一次模拟连接安全失效，复用物理负向事件的撤权处理；不代表实际拔线。授权立即失效，主进程核验基准后退出，辅助进程继续做退出后的独立核验。

在严格物理 HDMI 判断支持时，演练先启动连接观察器，再进行保护握手；候选监测启动失败则演练失败。就绪行和 `status` 的“连接观察”字段区分实际接线与无物理观察器的纯进程协议演练。未知／无法读取身份的负向事件、已追踪候选的 interest／termination、CG remove／disabled 都只撤销授权，不证明指定外屏已断开。撤权直接在事件线程标记，不等演练队列的握手或快照完成；晚到的 ready 及后续正向匹配不能重新授权。静默观察模式不为 CG 日志读取显示快照，避免阻塞候选通知队列。无物理观察器时，演练就绪只表示进程协议就绪，不能用作真实停用准入。

普通不含内屏责任的演练等待辅助进程退出后独立核验成功，确认无本轮进程，再执行 `--finalize-primary` 独立终验并清除记录。主进程仍活着时，不把辅助进程收到停止通知当作已退出。若核验不符，保留记录与保护；先恢复桌面可读状态，不删除记录启动新会话。握手失败时禁止控制；对无配置写入的演练记录，`--recover-primary` 可进行只读核验补偿。

日志的“通知至核验”仅是进程事件通知后的耗时，不能作为实际故障至恢复的 10 秒验收证据。`RecoveryTiming` 的离线自检使用合成的故障、通知和恢复时间戳，确认延迟通知仍计入总时长；原生时基为包含睡眠的 `mach_continuous_time`。物理拔线起点、误差与真实内屏可用恢复仍未完成验收。

离线计时检查不连接显示服务、不创建恢复记录；四个输入均须为同一连续单调时基下的 UInt64 纳秒值，分别表示故障的最早／最晚可能时刻、通知观测与恢复核验观测。例如以下合成输入中，通知到核验只有 2 秒，但故障至核验观测耗时范围是 10–11 秒，不能判为满足时限：

```sh
"$extilume_bin_dir/extilume-probe" --check-recovery-timing 0 1000000000 9000000000 11000000000
```

模型保留原始故障区间宽度，不把通知时刻当作物理动作上界。人工确认可以晚于通知或恢复核验；后一种情况下，耗时下界只能取 0。判定针对故障至核验观测：上界不超过 10 秒、下界大于 10 秒或区间跨越 10 秒。核验可能晚于实际恢复，因此观测超过 10 秒不能证明实际恢复超时；如故障在第 1 秒、实际恢复在第 3 秒、人工确认在第 4 秒，而第 16 秒才独立核验，观测耗时区间虽为 12–16 秒，实际恢复只用了 2 秒。这个计算不核实输入来源、通知归属或实际恢复，不能作为停用许可，也不能单凭计算完成 4.3／4.4。4.3 另需实际链路拔插、设备事件及独立桌面观测；4.4 在故障起点未知、只有候选通知或没有实际恢复效果证据时保持未完成，阶段二仍须真实停用全过程验收。

命令退出码 0 仅表示输入格式和顺序有效；时限判定须查看报告，不能由退出码推断验收通过。

`kill` 使用与原生 `ContinuousClock` 相同的 `mach_continuous_time` 和时间基数换算纳秒，包含睡眠时间。计时从终止动作前开始，到辅助进程已退出、独立原生终验成功并完成该测试目录收束后结束；这是无显示改动演练的保守耗时上界，包含通知和核验等待，不能把原生日志的“通知至核验”作为起点。该指标不表示实际内屏可用的恢复时间，不证明物理拔线或 10 秒硬验收通过。

保护协议交错检查同样无需拔插或显示写入：

```sh
python3 scripts/verify-guard-interleavings.py "$extilume_bin_dir/extilume-probe"
```

该脚本通过匿名 IPC 读取当前布局，建立目标等于基准、无内屏责任的 `applying` 记录；当前用户独有的临时目录和记录分别为 `0700`、`0600`。十一个场景覆盖父进程存活时的 IPC EOF、停止接管通知、辅助进程就绪前终止、旧代次记录拒绝、父进程退出后重读最新代次、不同会话替换、同会话代次回退、父进程保存 `restoring`、保存 `restored`、退出后的目录锁延期释放，以及原生重启交接。会话与原点组按 UUID 值比较，不以 UUID 大小写或 JSON 数组编码次序判断变化。父进程持锁期间独立恢复必须被拒绝；父退出后的核验、辅助进程实际退出与独立终验成功后才清理目录。失败保留责任，不杀其他任务进程。协议帧使用一个覆盖头部和负载的总 deadline；演练失败后脚本有界等待自己终止的父进程退出。

恢复阶段场景要求父进程存活时辅助进程保持等待且记录字节不变，父进程退出后继续独立核验；已经 `restored` 的记录核验后仍不得改写。锁延期场景由本 fixture 的短期子进程继承目录锁描述符并持有两秒；父进程退出后，辅助进程继续存活，竞争恢复被拒绝且记录不变，锁释放后才完成核验。这是受控锁延期释放，不证明独立第三方取得锁后的合法交接。受限日志核对取锁失败只记录一次，成功终验后才清理本 fixture 创建的日志。

不同会话检查要求旧辅助进程有限时间退出、记录字节不变且新恢复进程能取得锁；退出只表示责任不属于旧握手，不表示新责任已恢复。记录缺失、读取失败、损坏或同会话代次回退不能作为移交证据，仍保留保护和责任。同会话回退检查确认辅助进程未退出、冲突恢复被拒绝和记录未变，再仅结束本轮无显示改动 fixture 的辅助进程并独立核验收束。两项故障输入由驱动器直接替换测试记录，绕过了 `RecoveryStore.save` 对未决跨会话覆盖与代次回退的禁止；它们验证隔离防线，不证明合法重启的完整责任交接。

`native-restart-handoff` 仅暂停本 fixture 的旧辅助进程以模拟调度延迟。原父进程退出后先验证目录锁可取得，排除锁冲突，再确认新原生演练拒绝覆盖未决旧记录且记录字节不变。接任的 `--recover-primary` 通过真实存储流程恢复同一会话、代次和基准；旧辅助进程恢复调度后须成功独立核验并退出，不能再次改写已 `restored` 的记录。独立终验结清旧责任后，在同一目录启动新原生演练，验证新会话、同一基准、正常退出后的独立核验和最终清理。驱动器在超时、中断或后续断言失败时，仍向同用户、参数精确匹配本 fixture 目录的辅助进程发送 `SIGCONT`，保留责任记录供继续核验。此场景不直接替换会话记录，也不调用显示配置写入。

### 合并拔插验收

拔插按预先准备的批次安排，不随单个探针的开发反复要求用户操作：

- 先完成构建、离线故障自检、通知注册、时间基数核对及 `stop`／EOF 正常退出验证；任一失败先修复，不要求用户拔插。
- 开始前列清本批待证问题、各观察器及预期结果；同一链路、同一运行场景下，物理事件候选、原观察器、CoreGraphics 回调、独立短进程读回与计时记录共用一次拔出和一次插回。每次现场仍只提示一个动作。
- 候选事件尚未确认物理身份时，保持只读；不为合并检查提前启用内屏停用。合并采集不改变各任务的证据标准，只有断开观察而没有实际恢复时，不能算完整故障恢复计时通过。
- 没有事件或结果不符时先停止、分析已有记录；只有实现、事件来源或受影响环境发生实质变化，且新的预检通过、明确下一轮能回答的新问题后，才重新安排拔插。相同程序和条件下不重复碰运气。
- 已通过的主屏场景沿用原证据；影响控制／恢复的改动或系统、链路变化时，只重验受影响项。真实内屏保护的不同故障窗口及规定的至少三次重复仍须保留，集中安排，不能用一轮只读拔插抵扣。
- 用户正在使用主屏模式工作时，不自动退出应用、改变布局或触发拔插；提前约定实机窗口，完成一批后统一收束。详细日志继续保存在忽略的本地目录。

4.3 的有限结论是：两轮实际链路拔插均观察到 External VideoInterface 候选终止早于 CG，具备保守负向失效信号；最新一轮同时保留了本地动作界限、事件时间及独立桌面读回。候选精确绑定未知，因此不宣称它是目标特定断开识别，也不从其 matched 或陈旧 CG 列表推断可用。负向撤权不要求先证明是哪台设备断开；重新准入仍须独立证明目标身份、可用桌面及当前责任适用。4.3 据此完成观察验证，不表示已接入控制或恢复，更不表示 10 秒时限通过；4.4 保留未完成。相同实现和环境下不重复要求拔插。

观察入口必须实际取得至少一个 External 候选且全部注册成功才报告就绪；仅注册成功但集合为空不算就绪。候选存在也不等于完整观察覆盖或停用许可。5.1 仍须处理观察失败／未知事件、撤权与提交交错，以及主进程存活／死亡时的单一恢复执行者；恢复只能处理当前会话和代次的已有责任，不能借负向事件重放旧布局或清除未决责任。

### 只读物理事件观察

桌面唤醒、HDMI 已接入且唯一物理身份已确认时运行：

```sh
"$extilume_bin_dir/extilume-probe" --watch-connection
```

观察入口先精确匹配当前 HDMI 的 IOKit service，再同时监听目标 shim 和 `Location=External` 的 `DCPAVDeviceProxy`、`DCPAVServiceProxy`、`DCPAVVideoInterfaceProxy` 候选。输出目标服务的 interest、property-change、匹配／终止事件，以及候选类别、数值消息类型和 CG 回调；不输出设备路径或身份。初始排空标为 `initial-not-physical`，不算实际连接事件。

候选的 interest 或终止仅将本次观察的 `invalidated` 单向置为 true，表示安全条件不能继续确认，不能解释成目标 HDMI 已拔出；之后的 matched 和 CG 在线／活动列表不能清除该标记。候选可能由无关服务重建触发，不能提供目标身份、可用桌面或重新停用许可。此观察尚未接入控制／恢复路径；将来恢复请求仍须核对现有责任、身份、适用拓扑和用户配置来源，不直接回写旧基准。

事件记录包含相对单调毫秒及 `mach_continuous_time` 换算的 `continuousNs`；CG 时间戳在回调入队前取得，附带的活动数则在队列处理中读取，可能来自陈旧缓存，只用于排查，不证明物理外屏可用。时间戳表示用户态观察到通知的时刻，不是硬件断开时刻。输入 `mark` 是人工准备标记；`stop` 或输入 EOF 释放所有监听并退出。

IOKit 通用 SDK 声明不保证这条 HDMI 链路在拔线时产生 property-change 或 service termination，必须与实际拔线及新进程读回对应。没有目标设备事件或无法约束通知延迟时不能据此授权停用；人工标记至事件的间隔也不能冒充实际断开检测延迟。此入口不执行任何配置写入、不创建恢复记录。

范围判断必须拒绝镜像、多外屏、虚拟屏和无法确认物理身份的外屏。非内置、在线或主屏属性均不足以单独证明物理 HDMI 连接。

本机 HDMI 匹配在进程内精确比较 CoreDisplay 提供的设备位置与 IOKit 的注册路径；仅当匹配唯一、下游为 HDMI、EDID 身份非空且系统 UUID 可解析时才确认物理外屏。CoreDisplay 只读符号通过动态加载获取，私有符号或字段缺失即保持未知，不采用打分猜测。UUID 和设备路径不打印、不由只读入口落盘。此路径只验证本轮系统和 HDMI 链路，不扩大到其他连接方式。

## 恢复数据与来源

恢复模型只包含会话、事务代次、阶段、稳定显示身份、主屏和所有相关原点组成的布局组，以及单独的内屏启用位。分辨率、刷新率、旋转、亮度、颜色、窗口和 Spaces 不属于恢复负载，不能从旧快照回写。

- 初次 A → B 保留 A；已经确认的用户 C 在再次接管前成为新基准，C → B 之后恢复 C。
- 用户 C 后直接退出，未被重新接管的布局不生成回写计划。
- 自身回调和重连残留 B 保留原基准；提交或恢复期间的读回不能被提升为用户配置。
- 用户 C 已解除当前责任后，若完整读回再次出现已知应用 B，恢复责任重新标记，基准仍为 C；此前未决来源不会因此被清除。
- `confirmedUser` 表示调用方已有用户操作证据，不能仅凭等待结束或出现不同布局来传入该来源。来源未知时保留责任、停止新接管；运行时事件如何取得这个证据仍属于后续控制集成与实机验收。
- 恢复前重新映射稳定身份到当前数字 ID，同时读当前布局；数字 ID 重用、身份冲突、零 ID、无证据的 C 或无关屏均拒绝布局回写。
- 原主屏缺失时只计算适用部分的平移，缺失布局组责任保留；部分恢复读回不能清除完整布局责任。内屏启用位独立于布局来源，未恢复的启用责任仍提供安全恢复计划。

恢复成功须读回基准布局，以及记录中存在的内屏启用位；即使该启用位已无 pending 标记，也不能省略实际核验。当前主屏终验命令拒绝含内屏启用责任的记录，不替尚未实现的停用路径清除责任。

`RecoveryStore.apply` 的自检确认 prepared、applying 已落盘后才允许控制回调运行，回调失败保留责任；目录须当前用户所有且为 `0700`，记录为 `0600`，拒绝符号链接、非普通文件、损坏负载与放宽权限。未完成事务不可清除。原点控制入口已接入该守卫；真实文件系统写入失败、并发保护进程、系统回调来源交错和恢复后的实际桌面仍需后续任务逐项验证。

存储层要求同一实例先成功取得目录独占锁，才能调用 `save`、`clear` 或 `apply`；未持锁或取得锁失败时返回 `ownershipUnavailable`，不创建记录、不执行控制回调，也不能覆盖或清除另一实例的责任。`load` 仍允许保护进程在就绪握手前只读查看责任。实例由调用方串行访问；释放实例时关闭目录句柄并释放锁，接任者须重新取得锁并读回记录。

缺屏期间的被动观察保留完整基准；缺失布局不能被人工确认成完整 C，出现记录之外的显示身份也会转为未决来源。无写入保护演练与辅助进程通过独立短进程核对当前布局，避免长期进程缓存被当作退出后的恢复证据。

就绪读取及恢复模型的自动检查无需拔插：

```sh
swift test
python3 scripts/test_verify_guard_drill.py
```

保护演练脚本以同一个单调 deadline 等待完整就绪行，不预读后续消息；半行、EOF、非就绪首行或超过 4096 字节的首行均拒绝。
