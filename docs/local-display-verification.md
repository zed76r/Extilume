### D1 校准工具与准备状态

`scripts/calibrate-recovery-clock.py` 直接用 ctypes 读取原生 continuous／absolute tick 和时基；用 POSIX `CLOCK_MONOTONIC_RAW`／`CLOCK_UPTIME_RAW` 交叉核对换算，并用前后原生样本包围既有 probe 的 `--sample-recovery-clock`。采集只写当前用户所有的 0700 目录中新建的 0600 文件，不覆盖旧样本；二进制绑定及原始启动会话仅保存在私有文件，终端不输出身份或绑定值。POSIX 入口在 [Apple Libc 实现](https://github.com/apple-oss-distributions/Libc/blob/main/gen/clock_gettime.c)中使用同源 Mach 时钟，不是独立的物理休眠传感器。

离线 `compare` 要求同一启动会话、二进制及时基；恰好一组电源配对在两端样本的 continuous 和 awake 时间轴内完整有序。原生、Swift 外层和电源区间三组休眠界限均须有正下界、共同交集非空，且共同上界不超过电源事件窗口，才输出 `measurementSupported=true`。无配对、零下界或矛盾证据不通过；`hardwareAcceptance` 始终为 false，不能据此宣称画面、实际故障十秒或日常准入通过。

### 批次与现场配合

最终 App 的 F1–F5 可按三个基础批次共享准备，每批每组一次；该安排不在 D1、D2 之前执行，也不承诺三批完成全部覆盖。同一关键场景仍累计三次，各次单独判定。每个完整基础批次最多 **五个故障子轮、四次主进程终止、两次正常睡眠和一次 HDMI 拔插**；S1–S7 的具体分支和次数须事先计入冻结清单，不临场补项。

- 开批前一次完成当前候选／工具换绑、驱动就绪检查、日常会话交接、初始布局与责任记录保存，以及连续只读采集。现场授权须列出实际白名单、动作和上限；可明确授权连续多个批次，授权范围内不逐子轮重复询问许可。
- 每个子轮仍须新建归属明确的主辅会话，复核当前开盖、解锁、物理显示、保护及责任状态；上轮已恢复且无测试进程，才准许下轮停用。批内中间恢复到适用 C／准备布局，批末统一还原原完整布局和模式、结清并保留责任、重启日常外屏主屏会话。
- 使用现有恢复确认窗口一次记录实际可交互终点及画面正常确认；软件核验和用户确认后才继续，不在每个成功子轮后追加同义聊天确认。F1 醒后仅外屏的功能确认与故障后双屏恢复确认是不同检查点，分别保留。
- 用真实状态与完整身份核验判断就绪；不新增固定二十秒保持或一秒亮屏期限。外屏启动慢、内屏先恢复再关闭的正常过渡按原策略观察，不据亮屏先后判失败；原十秒故障清醒预算保持。
- 任何异常、手动显示救援、证据不全、最早起点丢失或无法证明时限，立即停止后续故障和停用，安全收束并保留原失败；不自动重试或现场补够次数。批内出现未决责任，不以重启日常应用代替恢复。

## 主动验证与停止

主屏命令已实现但尚未完成实机验收。用户明确启动单项试验时，保持开盖、单台已确认物理 HDMI 外屏与双屏非镜像桌面。准备当前用户独有、权限为 `0700` 的状态目录：

```sh
mkdir -m 700 .extilume-verification-state
extilume_bin_dir="$(swift build --show-bin-path)"
"$extilume_bin_dir/extilume-probe" --verify-primary .extilume-verification-state
```

托管环境取得构建目录时也要带上前述 module cache、`--disable-sandbox` 与 `--cache-path` 参数。目录已存在时先检查归属、权限与未决责任，不删除已有记录来启动新试验。入口取得目录独占锁；有任何恢复记录即拒绝新会话。

启动先连续读回相同配置；开盖、物理 HDMI 与双屏扩展条件不满足时保留事件监听，等待条件就绪，不创建新事务。符合条件后原子保存恢复责任，使用公开原点事务与 `.forAppOnly` 将整个布局平移到外屏为主屏。仅监听 CoreGraphics 回调与唤醒事件时进行有限重读，不持续轮询。输入 `status` 查看活动屏、主屏与事务数；已经是目标布局时，重复事件不会产生新事务。自动连接／唤醒生命周期尚未验收，不应依赖其自动接管。

主屏运行与只读事件观察入口使用 AppKit 的完整事件循环，激活策略为 `prohibited`，不创建窗口或抢焦点。CoreGraphics 回调只负责将工作送入串行队列；裸 `CFRunLoopRun` 或仅初始化 AppKit 不能替代这两个入口的事件处理。恢复、终验和短进程读回仍是执行后退出的命令。

手动在系统设置修改布局后，输入 `confirm-user` 明确确认此次操作来自用户，再输入 `reapply` 验证 C → B。`confirm-user` 不应由脚本按延时自动发送；不同布局或回调本身不能证明是用户修改。来源未知时保留责任并拒绝重新接管。

为避免持续进程的陈旧读回被当作当前配置，控制器使用同用户短进程进行稳定读回，通过匿名 IPC 返回快照，在提交前后和恢复前后核对；短进程完成后有界回收。原始身份只在内存与该 IPC 内传递，不进入参数或日志。确认 C 时要求实际布局不同于应用 B；无法取得独立观测即停止操作、保留责任，不把旧读回当作确认成功。正常稳定期间不持续启动观测进程。

连接与唤醒先等待 1 秒再观察及尝试接管，连续连接事件和等待期间仅含桌面形状变化的事件重新计时，避免立即把暂态双屏布局写成未决来源。断开立即观察；开始配置、其他设置事件、明确确认 C、手动重新接管或退出均取消待执行接管。系统回调还会立即撤销已经开始读回的接管意图，观察结束和坐标写入前再次检查，避免串行队列被读回阻塞时遗漏已到达的用户事件。等待时间不证明来源或硬件已经稳定，提交前的完整快照相等检查与提交后目标读回仍不可省略。事务失败会输出责任落盘、写入前读回、坐标写入、目标读回或应用确认落盘的阶段标签，不输出设备身份。

写入前的独立读回与取消检查属于无显示副作用的预检。预检失败且操作尚未调用时，记录持久化回可重试的 `owned`：旧 `owned` 的基准、已应用布局、内屏及来源标记均保留，代次维持本次更高值；即使用户 C 已使 pending 为 false，也保留旧应用布局以供退出补偿。没有旧 `owned` 时，已应用值回到基准、pending 为 false，记录仍保留待恢复与终验。取消状态保存失败、操作已经开始后失败或进程在 `applying` 落盘后直接死亡，仍保留磁盘上的未完成阶段，不能据此重试或清除责任。取消不确认陌生布局为用户 C。

若原进程已经退出，记录仍处于 `owned`，且你确认当前不同于应用 B 的布局是手动修改的 C，可先运行 `--confirm-user-primary <同一状态目录>`，再进行补偿；该确认命令只更新来源与恢复基准，不写显示配置。提交中或恢复中的记录不能用此命令改成新基准。重连读回已知 A 可保留原基准并等待重新应用；陌生布局或此前未决来源仍须明确确认。

输入 `stop`、发送 EOF 或按 `Ctrl-C` 时，程序只提交负责的原点布局到 `.forSession`，不写永久配置。正常停止后，责任记录保留到另一进程读回基准一致：

```sh
"$extilume_bin_dir/extilume-probe"
"$extilume_bin_dir/extilume-probe" --finalize-primary .extilume-verification-state
```

异常退出后的补偿命令为：

```sh
"$extilume_bin_dir/extilume-probe" --recover-primary .extilume-verification-state
"$extilume_bin_dir/extilume-probe" --finalize-primary .extilume-verification-state
```

来源未决的记录只有在没有内屏启用责任、两个独立短进程均读回完整保存基准时，`--recover-primary` 才可只确认已恢复，不写显示配置、不更改基准、会话或代次；记录仍保留到独立终验。此分支仅供原控制进程退出后使用，运行中的正常停止仍须显式提交当前 C，防止 `.forAppOnly` 的退出回退覆盖用户配置。合盖缺屏、主屏或原点不同、读回失败均返回失败并原样保留记录。可用下列无显示写入 fixture 自检该边界（只有双屏时才增加 pending 布局与同身份原点不同的原生案例，单屏会明确跳过）：

```sh
python3 scripts/verify-primary-reconciliation.py "$extilume_bin_dir/extilume-probe"
```

其他缺失身份、布局来源未知或恢复读回不符仍会保留责任并返回失败。不要输出或手动删除状态文件：其中含稳定显示身份，仅供当前用户恢复读取。该命令不处理内屏启用责任。内屏另有下述受保护验证入口；真实效果与故障恢复仍未验收，不能据此启用日常仅外屏模式。

主屏试验的停止条件是：主进程退出后，由独立观测确认最新用户配置 C 保留，且没有未决恢复责任。内屏停用试验还要求先读回内屏可用及适用配置恢复，再清理保护进程；恢复未完成不能仅靠结束进程收束。只读入口不创建控制事务，退出无需恢复。

### 主屏逐场景复现与判定

以下是验收方法，不是所有场景已通过的声明。主动场景只在用户明确启动、开盖与安全拓扑满足时执行；拔插和睡眠须另行安排，不由这张表自动触发。每项记录系统、连接链路、代码版本、输入、独立读回及未决责任；详细结果留在本地 `.local/verification/`。

| 场景 | 复现方法 | 判定依据 |
| --- | --- | --- |
| 开盖启动 A → B | 记录只读 A，运行 `--verify-primary`，独立读回 B，人工确认两屏桌面 | HDMI 主屏、内屏保留扩展桌面，相对位置不变 |
| 重复接管 | 在 B 上重复输入 `reapply`，再输入 `status` | 不增加事务数或代次；独立布局仍是 B |
| 正常退出 | 输入 `stop`，等待进程退出，独立只读及 `--finalize-primary` | 最终 A 一致；清除发生在退出后终验成功时 |
| 用户 C → B → 退出 | 手动修改主屏与位置，刷新率保持用户原选项；确认 `confirm-user` 后 `reapply`、`stop` | 独立终验保留最新 C 和刷新率，不恢复旧 A |
| 用户 C 后直接退出 | 手动修改 C 并明确 `confirm-user`，不重新应用，输入 `stop` | 退出后 C 与未控制设置保持一致 |
| 主进程强退及退出后重连 | 只强退本轮控制主进程；独立读回，再按现场安排拔插，最后补偿和终验 | 分别记录退出后与重连后的布局；不能据此证明存活期间自动重连 |
| 合盖启动与退出 | 保持合盖及可用外屏，启动控制器，分别验证 `stop`、EOF、`SIGTERM` | 只等待，事务数为 0；退出成功且无新增恢复记录，不证明开盖内屏停用 |
| 启动时缺外屏、运行中插入 | 现场确认内屏桌面可用，再分别从缺外屏状态启动、接入外屏 | 缺外屏时不控制；稳定且符合范围后自动接管，基准不得取旧 B |
| 存活期间断开与重连 | 控制器运行期间进行已安排的拔插，逐步独立读回 | 缺屏只处理适用责任且不清除完整责任；重连不把 B 保存为原状 |
| 睡眠唤醒及唤醒后 C 恢复 | 记录 C，按现场安排睡眠唤醒，核对稳定后接管与退出 | 自动接管恢复到最新 C，未控制设置保留；缺少实测则为未验证 |
| 物理事件观察 | 单独运行 `--watch-connection`，同时留存现场动作及独立读回 | 初次 `matched` 与人工 `mark` 不算物理事件；对照程序回调不能替代修复入口全链路验证 |

失败轮次保留失败结论和收束结果，修复后的通过记录单列。未执行的场景写明“未验证”，不能由构建、自检或其他场景的通过推定。主屏完整生命周期未通过时不允许阶段一准入。

## 不改显示设置的保护演练

私有启用位事务已实现隔离层，ABI 参考 [displayplacer 的声明](https://github.com/jakehilborn/displayplacer/blob/master/src/Header.h)。默认只读探测只解析 `CGSConfigureDisplayEnabled`，不调用该符号。事务在开始和提交前检查授权；配置失败或提交前撤权取消未提交事务，Complete 返回后不复用句柄。停用限定 `.forAppOnly`，恢复启用限定 `.forSession`，不设置显示模式或永久配置。真实停用仅提供下述显式本机验证入口，阶段二仍未准入。

`disableInternal` 要求已落盘的同一条 `applying` 责任、启用基准、开盖、严格双屏拓扑、外屏主屏及稳定的身份和数字 ID，快照前后再次核对记录和保护。新内屏责任还绑定本次启动会话 UUID 与内屏 IORegistry 对象 ID，握手同样绑定该 proof；普通演练的 nil 身份合同、不同 proof 或旧代次均不能授权停用。数字 ID 只是候选定位线索，不能替代身份核验。`checkProtection` 仍须核验辅助进程存活及恢复能力。

辅助进程在内屏合同就绪前解析启用符号，独立核对拓扑和活动内屏，并在发送 ready 前重读责任。父进程实际退出后，它取得目录独占锁，再读取最新同范围责任；需要时先启用内屏并独立读回，再按已有责任计算适用布局，只写原点。外屏缺失或布局来源未决不阻止安全启用，但会保留未完成的布局责任；完整布局和内屏状态均确认后才保存 `restored`，不自行清除记录。已恢复记录只核验，不重复写入。

假调用与记录测试覆盖符号缺失、提交前拒绝、保护撤销、身份和代次变化、真实活动子集确认、先启用后读取完整布局，以及停用刚提交后失去保护的恢复接管。后者要求主进程完成恢复或保活等待重试，不能把错误直接传播到进程退出。原生内屏合同无写入演练始终令启用位基准和目标均为 true，没有调用真实启停。这些检查不证明真实停用效果、硬件回调时序或 10 秒恢复；停用后内屏身份能否继续独立读回仍须实测，无法识别时保留责任，不能推断为已停用。

### 受保护内屏停用验证

当前仍阻断阶段二。首轮真实停用后，活动桌面仅剩外屏，独立内屏读回及正常恢复失败；主进程退出后未发现辅助进程存活，最终经仅启用事务手动救援。该失败不追溯改判。旧测试责任随后通过 `--recover-internal` 在保存基准下独立核验，正常收束为 `restored` 并保留，没有手改或删除记录。

2026-10-17 已确认两项独立问题：旧辅助进程与父进程共享 session/process group；同一内屏在自然合盖时返回的 CoreDisplay UUID 与开盖值不同。前者已改为独立 session，实际 PTY hangup 无写入回归通过，但不能据此确定首轮辅助进程的具体退出原因。后者新增启动会话与 IORegistry 对象绑定：只有新鲜读取的内置角色、同一 CoreDisplay 字典的数字 ID 与对象绑定均吻合，才允许保留责任中的 canonical UUID，并单独返回当前原始 UUID；重复身份或 proof 冲突仍拒绝。独立 witness 双读还必须核对原始 UUID 和 proof 均一致。完整快照只映射内屏身份标签，不修改布局、模式或刷新率。

内屏 witness 的双读结果通过明确的 IPC 响应返回：两次身份及硬件 proof 均合法但状态不同，才报告 `stateChanged`。主进程先确认子进程正常退出并回收，再还原为 `internalStateChanged`，使既有醒后稳定性重试可达（最多追加两次，每次延迟 0.3 秒），不把它误并成 EOF 通信失败。任一次身份／proof 不匹配或读取抛错均不发送该响应；未知响应、通信失败、异常退出、超时和清理失败仍不能进入此项重试。重读不解除故障、不清除恢复责任，也不改变连接事件撤权；该协议修复不证明旧实机身份冲突或仅外屏唤醒目标已解决。

原生预检已验证：以当前开盖 proof 和此前合盖 UUID 请求 witness，能保留当前原始 UUID 并完成映射；去掉 proof 则拒绝。内屏合同无写入启动、正常停止与退出后核验通过。后续真实停用中，事务返回成功，独立读回确认内屏不活动、同一硬件 proof 仍匹配，活动桌面仅含原物理外屏；这覆盖该次读回，不代表稳定停用全过程已验证。

撤权来源曾缩小到受控内屏的 `remove+disabled+desktopShapeChanged` 回调及同类代理服务的终止。只读登记发现这些代理同时存在 `External` 与 `Embedded` 角色，不能把 Embedded 代理直接绑定为内屏 UUID。此前额外订阅 Embedded 的 GeneralInterest，导致其未分类私有 interest 在就绪前撤权；该次失败保留，但这项额外订阅不是原规范的检测要求。当前持续观察实际外屏候选及目标服务的 interest，仅缓存 Embedded 的明确角色与类别。在显式停用合同内、非外屏目标、已登记角色且匹配终止类别一致时，还须现场读到 `Location == Embedded` 才单次排除；属性不可读不使用缓存回退。已消费 ID 不重新获得额度；角色／类别冲突、未知负向对象和重复终止仍撤权，迟到 matched 不重新授权。

父进程先落盘 `applying` 责任，再启动独立保护。保护就绪前核验启用符号、内屏身份、物理外屏与责任范围；父子进程使用 AppKit 事件循环，父进程控制工作不阻塞主事件循环。只有内屏 UUID、非零数字 ID、内置角色和完整拓扑一致，且保护仍就绪时，才允许开始和提交停用。CG 只豁免精确预期非零内屏的单独 disabled，或 remove+disabled 加可选 desktopShapeChanged；额外未知或冲突标志仍撤权。其他 remove／disabled、IOKit 负向候选、保护死亡或通信断开仍撤权。这些失效不会因恢复成功或唤醒而重新授权。

停用后分别由新进程读取活动桌面与模式无关的内屏状态：活动桌面须仅有原物理外屏，内屏须能重新核对身份且不活动。记录格式 v3 在 v2 的完整基准、停用前布局及活动子集上增加内屏硬件 proof，新内屏握手使用 v2；停用不伪造旧双屏布局作为读回。恢复比对使用停用前布局，恢复过程不生成新的用户基准。旧 v1／v2 记录仍可读取，但不会补造 proof，也不能授权新停用。试验期间不要替换或重新编译运行中的二进制。

输入 `status` 查看固定状态，输入 `stop` 恢复退出。正常退出或保护失效时，主进程先安全启用内屏、独立确认，再恢复可适用的布局；主进程死亡后由辅助进程取得锁执行同样步骤。启动事务在可能写入后失败，也由主进程接管恢复。恢复失败时保留进程、锁和责任，前十秒内作有界重试，之后等待显示事件或手动 `stop`；不以超时为理由退出保护，不清除未决记录。来源未决时不写原点；若两次完整独立读回已经等于保存基准，只确认恢复，不改写基准。

5.3 的原型另提供 `restore`、`confirm-user`、`reapply`：`restore` 核验恢复后暂停，保护进程继续运行，不发送退出握手；只有完整恢复且同一硬件 proof 仍吻合，记录才可返回观察状态。手动设置双屏 C 后，`confirm-user` 明确确认当前布局和内屏启用位，只更新基准，不抢回设置；运行中由用户自行恢复内屏并设置的完整 C 也可直接确认。`reapply` 要求当前布局仍等于已确认 C，先落盘同会话新代次的 `applying`，再仅以原点平移切到外屏主屏并停用内屏；正常退出仍恢复最新 C。原保护进程沿用到父进程真实退出，再独立读取最新代次；每轮重建连接观察器，不重置已经锁存的失效。

当前候选实现：主控、辅助进程及显式恢复入口均先注册独立系统电源观察。`SystemWillSleep` 只原子关闭新事务门禁，保留模式意图、最新 C、退出请求、故障和责任，并及时确认电源通知；不等待控制队列、内屏启用或配置提交。`SystemHasPoweredOn` 后先启用并独立核验内屏、恢复适用 C，再在原外屏身份、保护、来源与稳定性均满足时重新应用仅外屏。恢复后的明确快照抖动和重应用的暂态不稳定各最多尝试三次；真实事务失败、身份冲突、来源未决和保护失效仍锁存。手动暂停、退出及既有故障均阻止自动重应用。已进入的原生调用按实际返回值和句柄消费结果处理，不与补偿并发；每个新 begin/configure/complete 均重新检查门禁。未完成恢复的记录继续保留。

门禁版本已做首轮真实睡眠复验，但未重新进入仅外屏，仍不通过；结果见下方逐场景表。本次新增诊断仅完成离线验证，不证明冻结、异常亮光或醒后双屏问题已经修复。下列旧版睡前等待与失败记录保留历史结论，不作为当前候选的操作说明。

历史实现（已被上述门禁方案替换）：在睡眠通知回调返回前，最多等待十秒完成控制队列恢复与独立核验，预算包括排队；已暂停的会话也重新核验，不直接报成功。同一控制队列上的回调只延后恢复、不等待自己或重入应用；等待失败、超时或保护丢失仍锁存失效，恢复任务与责任继续保留。早醒及重叠通知须等全部准备完成，迟到恢复不能重新授权。此处理依据 [Apple 睡眠通知约定](https://developer.apple.com/documentation/appkit/nsworkspace/willsleepnotification)，没有把未知私有消息列为安全事件。293 项 Swift 测试通过，但修正版真实睡眠复验仍失败：睡前恢复等待超限，用户报告唤醒后内屏亮起、画面卡死及外屏菜单栏异常亮光。主辅退出、记录标记 `restored` 不足以证明实际桌面正常；用户再次开盖确认双屏可操作后，才独立核对完整最新 C、模式及原日常记录恢复。原失败保留，5.3 继续未完成，不再进行新的停用测试。十秒等待预算不替代实际故障至恢复的十秒验收。

原控制进程已经退出时，可对原状态目录显式运行 `--recover-internal`。该入口取得独占锁，重读原责任，先确认或启用内屏，再按原责任核验与恢复适用布局；不会重新停用或清除记录。旧记录缺少 proof 时仍须匹配原 UUID，不能凭保存的数字 ID 绕过身份检查。已 `restored` 的记录只核验，不重复写入。

历史独立通知版本（等待恢复的时序已被替换）：采用 [Apple 公开系统电源通知](https://developer.apple.com/library/archive/qa/qa1340/_index.html)，注册成功才准入停用。在独立通知队列有界等待恢复，不阻塞 AppKit 投递线程；准备成功、失败或超限均先调用一次 `IOAllowPowerChange`，再继续停止或等待唤醒。启动失败先退出控制队列再排空电源回调；确认前延后的退出请求在确认后继续执行。仅 `SystemHasPoweredOn` 触发唤醒检查，不取消睡眠、不修改锁屏设置。连续时钟复核预算，迟到完成或时钟不可用不能重新授权。生命周期日志只记录固定阶段、角色、连续时钟、线程类别及结果，覆盖启用、独立读回、原点恢复和首个负向事件；详细日志仍仅留在受限忽略目录。这修正了已确认的等待与退出竞态；随后真实复验仍未恢复睡前仅外屏模式，不证明目标问题已修复，5.3 仍未完成。

此修正的离线验证为 308 项 Swift、21 项 Python 测试通过，覆盖启动持久化失败后的电源回调排空、确认前延后退出及确认后继续退出、迟到恢复和连续时钟异常。另仅注册／注销电源通知三次，未触发睡眠、未调用显示写入；前后完整布局、模式和日常恢复记录一致，仅原日常主屏应用保留运行。该烟测不覆盖真实电源通知到达、睡眠期间显示服务行为或通知并发注销。

成功停用的日志仅表示软件读回成立；5.2 的现场输入、边界及正常亮屏恢复结论见下表。5.3–5.5 仍须完成相应生命周期、故障时点及物理故障起点计时。代码中的恢复重试窗口不是实际故障至恢复的十秒保证。本入口不接入日常菜单，当前不自动清除内屏恢复记录。

### 无写入演练用法

保持桌面唤醒，使用同一空的 `0700` 状态目录：

```sh
"$extilume_bin_dir/extilume-probe" --guard-drill .extilume-verification-state
```

内屏合同接线使用 `--guard-drill-internal` 和另一个空的 `0700` 目录，要求开盖、外屏主屏及严格双屏范围。它记录的内屏基准与目标均为启用，不创建停用责任；其已恢复记录保留供复核，不能使用仅支持主屏责任的 `--finalize-primary` 清除。

演练记录当前布局，目标等于基准，不调用原点或启用位写 API。它用 `posix_spawn` 和 `POSIX_SPAWN_SETSID` 启动同用户独立辅助进程，通过匿名 socket 传递会话、代次与父进程身份，避免父进程控制终端的进程组 hangup 同时结束保护。辅助进程验证受限记录、注册父进程退出事件后回复就绪。授权自检拒绝未就绪、错误合同、旧代次及失效后重握手；新握手验证失败会立即撤销旧就绪授权。演练期间不得搬移或替换状态目录。

- `status`：核对保护仍就绪；稳定期间采用进程与 IPC 事件等待，不定期读取显示列表。
- `stop`：主进程核验基准、保存恢复状态，通知辅助进程停止新接管。辅助进程继续等到主进程实际退出，再独立读回，退出后记录仍保留。
- `crash`：只让演练主进程异常退出；辅助进程取得原目录独占锁，重读最新同会话记录并核验实际基准，保存恢复结果后退出。
- `lose-guard`：只终止本演练启动的辅助进程；主进程撤销授权，核验并退出，不继续控制。
- `invalidate-connection`：注入一次模拟连接安全失效，复用物理负向事件的撤权处理；不代表实际拔线。授权立即失效，主进程核验基准后退出，辅助进程继续做退出后的独立核验。

在严格物理 HDMI 判断支持时，演练先启动连接观察器，再进行保护握手；候选监测启动失败则演练失败。就绪行和 `status` 的“连接观察”字段区分实际接线与无物理观察器的纯进程协议演练。未知／无法读取身份的负向事件、已追踪候选的 interest／termination、CG remove／disabled 都只撤销授权，不证明指定外屏已断开。撤权直接在事件线程标记，不等演练队列的握手或快照完成；晚到的 ready 及后续正向匹配不能重新授权。静默观察模式不为 CG 日志读取显示快照，避免阻塞候选通知队列。无物理观察器时，演练就绪只表示进程协议就绪，不能用作真实停用准入。

普通不含内屏责任的演练等待辅助进程退出后独立核验成功，确认无本轮进程，再执行 `--finalize-primary` 独立终验并清除记录。主进程仍活着时，不把辅助进程收到停止通知当作已退出。若核验不符，保留记录与保护；先恢复桌面可读状态，不删除记录启动新会话。握手失败时禁止控制；对无配置写入的演练记录，`--recover-primary` 可进行只读核验补偿。

日志的“通知至核验”仅是进程事件通知后的耗时，不能作为实际故障至恢复的 10 秒验收证据。`RecoveryTiming` 的离线自检使用合成的故障、通知和恢复时间戳，确认延迟通知仍计入总时长；原生时基为包含睡眠的 `mach_continuous_time`。物理拔线起点、误差与真实内屏可用恢复仍未完成验收。

离线计时检查不连接显示服务、不创建恢复记录；四个输入均须为同一连续单调时基下的 UInt64 纳秒值，分别表示故障的最早／最晚可能时刻、通知观测与恢复核验观测。例如以下合成输入中，通知到核验只有 2 秒，但故障至核验观测耗时范围是 10–11 秒，不能判为满足时限：

```sh
"$extilume_bin_dir/extilume-probe" --check-recovery-timing 0 1000000000 9000000000 11000000000
```

模型保留原始故障区间宽度，不把通知时刻当作物理动作上界。人工确认可以晚于通知或恢复核验；后一种情况下，耗时下界只能取 0。判定针对故障至核验观测：上界不超过 10 秒、下界大于 10 秒或区间跨越 10 秒。核验可能晚于实际恢复，因此观测超过 10 秒不能证明实际恢复超时；如故障在第 1 秒、实际恢复在第 3 秒、人工确认在第 4 秒，而第 16 秒才独立核验，观测耗时区间虽为 12–16 秒，实际恢复只用了 2 秒。这个计算不核实输入来源、通知归属或实际恢复，不能作为停用许可，也不能单凭计算完成 4.3／4.4。4.3 另需实际链路拔插、设备事件及独立桌面观测；4.4 在故障起点未知、只有候选通知或没有实际恢复效果证据时保持未完成，阶段二仍须真实停用全过程验收。

命令退出码 0 仅表示输入格式和顺序有效；时限判定须查看报告，不能由退出码推断验收通过。

修订后的计时保留连续总时长结论，另报告清醒恢复上界：`总时长上界 − 已证明休眠下界`。故障前、故障后、通知和恢复四个端点须来自采集时的同一启动会话，且与休眠证据的启动会话匹配。配对样本使用 `mach_continuous_time` 和 `mach_absolute_time`，均按系统时基转换成纳秒；采样区间与取整误差向保守方向扩展。电源通知间隔、熄屏、软件计时器停顿或单独的 sleeping 标志不能作为扣除依据。缺失、重叠、跨启动会话或无法定位的区间均不扣除，清醒等待和通知延迟仍计入；旧失败记录不改判。

只读采集器不主动睡眠、不改显示配置。先创建本轮私有目录并启动采集，结束时在该终端输入 `stop`；证据以 `0600` 新文件写入，拒绝覆盖：

```sh
timing_log_dir="$(mktemp -d .local/verification/suspend-timing-XXXXXXXX)"
chmod 700 "$timing_log_dir"
(
  umask 077
  python3 scripts/verify-suspend-timing.py record --probe "$extilume_bin_dir/extilume-probe" --evidence "$timing_log_dir/suspension.json" > "$timing_log_dir/session-notifications.log"
)
```

采集器主线程运行通知所需的 RunLoop，后台读取输入；`stop` 与 EOF 都正常收束、移除观察并保存证据。stdout 另记录固定名称的锁／解锁广播接收时间，脚本会保留此输出；上例将其保存为私有日志，不改变休眠证据 JSON 格式。`com.apple.screenIsLocked`／`com.apple.screenIsUnlocked` 没有已确认的公开语义，记录明确标注 `unverified-distributed-notification`。[Apple 分布式通知约束](https://developer.apple.com/documentation/foundation/distributednotificationcenter) 允许延迟或丢失，且通知不是可信通信：接收时间不等于实际解锁时间，未收到也不能证明尚未解锁，更不能用于控制准入、解除故障或扣除休眠。

主辅与独立 witness 的 stdout／stderr 也须保存在同轮忽略目录。witness 的 `internalIdentityRejected` 细分候选无匹配、重复身份、内置角色、硬件 proof 等拒绝原因；`internalCandidateUnavailable` 细分信息、数字 ID 和 UUID 不可读原因，仅包含固定枚举、连续时间及是否匹配数字提示，不包含身份值。身份拒绝和通信错误仍拒绝继续；合法双读变化通过前述明确响应保留，不再降为通信错误。需关联子进程记录，广播与拒绝记录的先后只能提供排查线索，不能证明因果。只读拔插投递样本不追认旧停用失败，也未验证受保护会话的通知时序。

连接观察另输出 `connection-observation` JSON：候选的已登记角色和类、事件种类、原始 `messageType` 数值、固定分类的 `Location`、撤权状态，以及观察器内的候选序号。interest 回调另记 `messageArgument=zero/one/other`，只分类参数位形；`nil` 归零，不解引用、保留或输出原始指针，不直接解释为音频／视频。其他事件不带该字段。角色取自状态机缓存，负向事件保留撤销前的角色；序号仅在同一 `role`／`observerStartedAtNanoseconds` 内用于关联，不代表物理身份。`registryScope=other` 只说明对象 ID 不等于目标或内屏 proof，不证明与它们无关；不输出原始 ID、UUID 或任意属性值。记录不新增注册表读取，也不改变未知事件撤权或 Embedded 额度。

interest 记录另有仅供诊断的 `messageClassification`：已登记 External 且类已知的候选，按下述实现线索区分 `protectionChanged`、音频／视频的 linkStart／linkStarted／linkStop／linkStopped；未知代码、链路参数缺失或非零／一、未登记或其他候选角色一律 `unknown`。非 interest 事件不带该字段。分类在现有撤权后的记录路径计算，不被授权或恢复状态机读取，不跳过任何失效。此旁路分类已做离线测试，并在内屏保持活动的一轮实际拔插中采到音频／视频及未知分类；未验证内屏停用期间的故障。

CG 回调另输出 `display-connection-observation`，使用同一异步输出队列：包含角色、观察器开始时间、回调入口采集的连续时间、完整原始 `flags`、固定 `scope=unknown/expected-internal/other`，以及既有判定函数的固定 `invalidationReason`（无原因时省略）。不记录 display ID、注册表 ID 或 UUID；`other` 不代表目标或无关设备。负向回调仍先执行原有撤权，再将诊断入队，不等待观察队列上的显示快照；正向或未分类 flags 也保留原值，不以缺少失效原因证明桌面可用。控制会话即使关闭普通事件文本输出也记录此字段，便于同轮比较保护／音频消息与后续 CG 失效的接收时间；未增加任何系统读取或改变恢复行为。该新增记录已做离线编码、scope、未知 flags 和慢输出测试，并在只读实际拔插中采到 CG 移除事件；不保证全部回调投递或注销等待语义。

不同会话检查要求旧辅助进程有限时间退出、记录字节不变且新恢复进程能取得锁；退出只表示责任不属于旧握手，不表示新责任已恢复。记录缺失、读取失败、损坏或同会话代次回退不能作为移交证据，仍保留保护和责任。同会话回退检查确认辅助进程未退出、冲突恢复被拒绝和记录未变，再仅结束本轮无显示改动 fixture 的辅助进程并独立核验收束。两项故障输入由驱动器直接替换测试记录，绕过了 `RecoveryStore.save` 对未决跨会话覆盖与代次回退的禁止；它们验证隔离防线，不证明合法重启的完整责任交接。

### 合并拔插验收

拔插按预先准备的批次安排，不随单个探针的开发反复要求用户操作：

- 先完成构建、离线故障自检、通知注册、时间基数核对及 `stop`／EOF 正常退出验证；任一失败先修复，不要求用户拔插。
- 开始前列清本批待证问题、各观察器及预期结果；同一链路、同一运行场景下，物理事件候选、原观察器、CoreGraphics 回调、独立短进程读回与计时记录共用一次拔出和一次插回。每次现场仍只提示一个动作。
- 候选事件尚未确认物理身份时，保持只读；不为合并检查提前启用内屏停用。合并采集不改变各任务的证据标准，只有断开观察而没有实际恢复时，不能算完整故障恢复计时通过。
- 没有事件或结果不符时先停止、分析已有记录；只有实现、事件来源或受影响环境发生实质变化，且新的预检通过、明确下一轮能回答的新问题后，才重新安排拔插。相同程序和条件下不重复碰运气。
- 已通过的主屏场景沿用原证据；影响控制／恢复的改动或系统、链路变化时，只重验受影响项。真实内屏保护的不同故障窗口及规定的至少三次重复仍须保留，集中安排，不能用一轮只读拔插抵扣。
- 用户正在使用主屏模式工作时，不自动退出应用、改变布局或触发拔插；提前约定实机窗口，完成一批后统一收束。详细日志继续保存在忽略的本地目录。


观察入口先精确匹配当前 HDMI 的 IOKit service，再同时监听目标 shim 和 `Location=External` 的 `DCPAVDeviceProxy`、`DCPAVServiceProxy`、`DCPAVVideoInterfaceProxy` 候选。输出目标服务的 interest、property-change、匹配／终止事件，以及候选类别、数值消息类型和 CG 回调；不输出设备路径或身份。初始排空标为 `initial-not-physical`，不算实际连接事件。

候选的 interest 或终止仅将本次观察的 `invalidated` 单向置为 true，表示安全条件不能继续确认，不能解释成目标 HDMI 已拔出；之后的 matched 和 CG 在线／活动列表不能清除该标记。候选可能由无关服务重建触发，不能提供目标身份、可用桌面或重新停用许可。负向观察已接入显式内屏验证入口的撤权／恢复请求；恢复仍核对现有责任、身份、适用拓扑和配置来源，不直接回写旧基准。

事件记录包含相对单调毫秒及 `mach_continuous_time` 换算的 `continuousNs`；CG 时间戳在回调入队前取得，附带的活动数则在队列处理中读取，可能来自陈旧缓存，只用于排查，不证明物理外屏可用。时间戳表示用户态观察到通知的时刻，不是硬件断开时刻。输入 `mark` 是人工准备标记；`stop` 或输入 EOF 释放所有监听并退出。

IOKit 通用 SDK 声明不保证这条 HDMI 链路在拔线时产生 property-change 或 service termination，必须与实际拔线及新进程读回对应。没有目标设备事件或无法约束通知延迟时不能据此授权停用；人工标记至事件的间隔也不能冒充实际断开检测延迟。此入口不执行任何配置写入、不创建恢复记录。

范围判断必须拒绝镜像、多外屏、虚拟屏和无法确认物理身份的外屏。非内置、在线或主屏属性均不足以单独证明物理 HDMI 连接。

本机 HDMI 匹配在进程内精确比较 CoreDisplay 提供的设备位置与 IOKit 的注册路径；仅当匹配唯一、下游为 HDMI、EDID 身份非空且系统 UUID 可解析时才确认物理外屏。CoreDisplay 只读符号通过动态加载获取，私有符号或字段缺失即保持未知，不采用打分猜测。UUID 和设备路径不打印、不由只读入口落盘。此路径只验证本轮系统和 HDMI 链路，不扩大到其他连接方式。

## 恢复数据与来源

恢复模型只包含会话、事务代次、阶段、稳定显示身份、主屏和所有相关原点组成的布局组，以及单独的内屏启用位。分辨率、刷新率、旋转、亮度、颜色、窗口和 Spaces 不属于恢复负载，不能从旧快照回写。

- 初次 A → B 保留 A；已经确认的用户 C 在再次接管前成为新基准，C → B 之后恢复 C。
- 用户 C 后直接退出，未被重新接管的布局不生成回写计划。
- 自身回调和重连残留 B 保留原基准；提交或恢复期间的读回不能被提升为用户配置。
- 用户 C 已解除当前责任后，若完整读回再次出现已知应用 B，恢复责任重新标记，基准仍为 C；此前未决来源不会因此被清除。
- `confirmedUser` 表示调用方已有用户操作证据，不能仅凭等待结束或出现不同布局来传入该来源。来源未知时保留责任、停止新接管；运行时事件如何取得这个证据仍属于后续控制集成与实机验收。
- 恢复前重新映射稳定身份到当前数字 ID，同时读当前布局；数字 ID 重用、身份冲突、零 ID、无证据的 C 或无关屏均拒绝布局回写。
- 原主屏缺失时只计算适用部分的平移，缺失布局组责任保留；部分恢复读回不能清除完整布局责任。内屏启用位独立于布局来源，未恢复的启用责任仍提供安全恢复计划。

恢复成功须读回基准布局，以及记录中存在的内屏启用位；即使该启用位已无 pending 标记，也不能省略实际核验。当前主屏终验命令拒绝含内屏启用责任的记录，不替内屏路径清除责任。v2 的停用前布局仅用于恢复匹配，不包含模式，也不能替代用户基准；缺失外屏时保留其布局责任。

`RecoveryStore.apply` 的自检确认 prepared、applying 已落盘后才允许控制回调运行，回调失败保留责任；目录须当前用户所有且为 `0700`，记录为 `0600`，拒绝符号链接、非普通文件、损坏负载与放宽权限。未完成事务不可清除。原点控制入口已接入该守卫；真实文件系统写入失败、并发保护进程、系统回调来源交错和恢复后的实际桌面仍需后续任务逐项验证。

存储层要求同一实例先成功取得目录独占锁，才能调用 `save`、`clear` 或 `apply`；未持锁或取得锁失败时返回 `ownershipUnavailable`，不创建记录、不执行控制回调，也不能覆盖或清除另一实例的责任。`load` 仍允许保护进程在就绪握手前只读查看责任。实例由调用方串行访问；释放实例时关闭目录句柄并释放锁，接任者须重新取得锁并读回记录。

缺屏期间的被动观察保留完整基准；缺失布局不能被人工确认成完整 C，出现记录之外的显示身份也会转为未决来源。无写入保护演练与辅助进程通过独立短进程核对当前布局，避免长期进程缓存被当作退出后的恢复证据。

就绪读取及恢复模型的自动检查无需拔插：

```sh
swift test
python3 scripts/test_verify_guard_drill.py
```

保护演练脚本以同一个单调 deadline 等待完整就绪行，不预读后续消息；半行、EOF、非就绪首行或超过 4096 字节的首行均拒绝。
