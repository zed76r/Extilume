# 菜单栏外屏主屏模式

双模式开发构建已进入实现，真实仅外屏的使用边界与隔离构建见[双模式开发 App](internal-display-app.md)。下文是已验收的固定外屏主屏版本；新开发构建不自动替换它。

已保留的固定模式 App 显示“模式：外屏主屏”，没有常驻控制窗口或内屏停用入口；该映像已完成18/18本机验收。此结论不扩展到当前双模式开发构建。

## 已验收映像与启动

当前构建脚本生成双模式开发包，见[开发构建说明](internal-display-app.md)，不会重建或替换本页已验收映像。正常交接并核对原责任后，可使用保留的日常产物：

```sh
open dist/Extilume.app
```

保留的本地产物位于忽略的 `dist/`，未经 Developer ID 签名或公证，未安装为发布版本。应用默认使用当前用户 `Application Support/Extilume`，只在目录不存在时创建 `0700` 目录；已有目录的权限、归属、符号链接及独占锁由恢复存储校验，不自动放宽权限。开发验收可使用已存在的独立 `0700` 目录：

```sh
mkdir -m 700 .local/menu-bar-state
dist/Extilume.app/Contents/MacOS/Extilume --state-directory .local/menu-bar-state
```

自定义目录必须事先存在且满足存储校验；无效参数、非安全目录或目录已被另一实例占用时，在创建菜单栏前明确失败，不回退到默认目录。目录已存在时先核对未决责任，不删除记录重新启动。不输出或分享状态文件，其中包含恢复所需的显示身份。

## 自动应用与范围

启动、连接、重连及系统唤醒沿用串行控制队列和稳定读回。连接与唤醒合并等待，提交前后分别读回；已经满足目标时不反复写入。只写主屏和原点，不写分辨率、刷新率、旋转、亮度或内屏启用位。

没有外屏时显示“等待外屏连接”，不创建显示事务。镜像、多外屏、虚拟屏或物理身份无法确认时显示原因，不自动解除镜像。支持范围仍限定为阶段零验收的当前 Mac、开盖、单台已验收物理 HDMI 直连及双屏非镜像桌面；其他连接链路没有获得新验收。

用户手动修改后，应用显示“请确认退出时恢复的排列”并停止新接管。要将当前布局作为退出时恢复的配置，请点击“设为恢复布局”。这个动作只保存恢复基准，不切换主屏；成功后显示“排列已确认，可切换主屏”，可点击“设为外屏主屏”主动接管，也可等待下一次连接或唤醒，退出时恢复已保留的配置 C。普通回调或稳定布局不会自动确认 C，本应用自己的目标 B 也不能保存为新基准。

确认要求开盖、完整且稳定的已支持双屏，以及与原基准相同的显示身份。保存前重复读回，收到显示配置、睡眠、唤醒或退出事件就取消确认；最后核对通过后原子保存一次。提交后的新事件按新变化处理，不回滚已确认的 C。保存失败显示“排列确认失败”并保留原责任，可以重试；不能确认存储状态时显示“恢复未完成”并停止新接管。退出失败后确认配置不会重新开启自动接管，仍需再次恢复并退出。当前链路已通过确认 C 后实际睡眠唤醒、重新接管、退出独立恢复 C 及重启核对；其他连接链路和事件交错仍需单独验收。

合盖期间不执行新控制。只有同一会话确实观察到合盖后，开盖使内屏重新连接，且完整布局仍为原基准或原目标、此前及期间没有未决来源时，才按重连合并后再接管，保持原基准。没有合盖观测、期间出现陌生完整布局或已有来源未决时，不以开盖推测配置来源。

睡眠前使用 [NSWorkspace.willSleepNotification](https://developer.apple.com/documentation/appkit/nsworkspace/willsleepnotification) 同步设置写入门禁，唤醒通知再由串行队列解除并合并接管。门禁覆盖启动、重试和写前读回；睡眠取消后不补写恢复，期间观察到陌生布局或此前已未决时仍停止接管，不用唤醒追溯推测来源。

## 菜单和故障处理

菜单沿用系统菜单结构，使用文字表达状态，不依赖颜色。入口图标由现有品牌显示器与收束光几何单色化，采用 template 自动适配明暗外观；图标不区分模式。固定入口包括模式、实际状态、打开显示设置与退出并恢复；只有状态适用时才显示重试动作。方向键、回车和 Esc 已实测；已生效入口的旁白名称已确认包含应用名、模式及状态，11 种注入状态的原生菜单呈现已逐项核对。

| 状态 | 可执行动作 |
| --- | --- |
| 等待、不支持、已生效 | 打开显示设置、退出并恢复 |
| 排列已确认，可切换主屏 | 设为外屏主屏、打开显示设置、退出并恢复 |
| 排列已确认，可以退出 | 保留退出意图，允许再次退出，不显示重新接管动作 |
| 正在应用 | 不允许并发重试；可以请求退出并恢复 |
| 应用失败，已恢复 | 重试、打开显示设置、退出并恢复 |
| 请确认退出时恢复的排列、排列确认失败 | 确认当前排列、重试恢复、打开显示设置；禁止新接管 |
| 恢复未完成 | 重试恢复、打开显示设置；禁止新接管 |
| 恢复失败，尚未退出 | 仍持有布局责任时可确认当前排列；重试恢复；应用仍运行，恢复确认前不正常退出 |
| 显示器未齐，等待恢复退出 | 开盖或接回原外屏后点重试恢复；不允许确认不完整配置或重新接管 |

退出请求立即撤销待执行的接管，等待串行事务结束，再恢复负责的布局并读回。恢复失败取消退出，不通过结束进程掩盖未决责任。重复点击不会并发执行控制或恢复。

显式“重试恢复”或退出时，若未决责任只涉及布局、两次完整独立读回均为已存原基准，可提交同一原基准的会话锚定，再读回确认恢复；成功后才解除来源未决，记录仍保留到退出后终验。这不会把当前陌生布局更新为新 C；不同布局、缺屏、身份变化或任一失败继续保留责任。

开发进程收到 `SIGINT` 或 `SIGTERM` 时也走上述正常退出流程，恢复失败仍保持运行。`SIGKILL` 无法执行退出恢复，不应以此绕过故障。退出完成回复通过主 RunLoop 送达，避免 `terminateLater` 的嵌套事件循环阻塞主队列回调。

## 退出后与旧记录

合盖导致内屏不可用，或原外屏缺失时，不能确认完整 C，正常退出会取消并保留责任。独立读回确认缺屏后显示“显示器未齐，等待恢复退出”，状态和恢复入口提示开盖或接回原外屏。两屏回来后点击“重试恢复”，继续完整恢复退出流程；等待期间不重新接管，也不能把不完整桌面确认为新 C。读取失败等其他错误仍显示“恢复失败，尚未退出”。

新增等待状态已有进程内菜单与控制器回归覆盖；此前 11 种状态的桌面呈现证据不扩展为新增状态已完成实际菜单呈现验收。

正常退出前的恢复确认不证明 `.forAppOnly` 作用域结束后的最终配置。当前保留恢复记录，需在进程退出后通过原生探测程序独立终验；不会仅凭进程内成功删除记录：

```sh
swift build --product extilume-probe
extilume_bin_dir="$(swift build --show-bin-path)"
"$extilume_bin_dir/extilume-probe"
"$extilume_bin_dir/extilume-probe" --finalize-primary "$HOME/Library/Application Support/Extilume"
```

使用自定义目录时把最后一个参数改为原目录；托管环境的构建命令须同样带缓存和 `--disable-sandbox` 参数。终验失败保留记录，不手动删除。异常结束后先运行 `--recover-primary <原目录>`，退出后再独立核对和终验；来源未决且当前布局不是完整基准时不会猜测或覆盖用户配置。完整恢复操作说明见[本机验证](local-display-verification.md)。

重新启动菜单栏应用时，先取得原目录独占锁，读取并处理旧责任；旧进程退出后的独立读回确认完整基准后才可清除旧记录并开始新接管。目标缺失、身份不匹配、来源未知或记录损坏均保留责任，不能以新运行覆盖。当前链路单轮强退回退与重启处理已验收；异常退出与再次连接、睡眠等交错仍待单独验收。

若旧主屏记录为已恢复、没有待恢复部分和内屏启用位责任，但重开时排列已不同，则显示未确认状态。用户可明确点击“设为恢复布局”选择新的恢复目标；完整同组身份、稳定读回且不是旧应用目标时才原子保存新的零改动会话，不删除旧记录来绕过来源保护，也不把旧目标追认为退出终验通过。随后可点击“设为外屏主屏”或直接退出。确认后再出现陌生排列仍会阻止接管；未完成的旧责任不能走此替代路径。

上述重启确认、显式应用和“排列已确认，可以退出”状态已有控制器与菜单对象测试；新文案尚未计入原 11 种状态的真实桌面呈现验收，新增流程的正常退出与重启仍需单独验证。

## 当前验证边界

当前 Mac 的主屏模式本机验收已完成（18/18）：控制与恢复关键路径已有实机证据，11 种注入状态菜单的桌面呈现、键盘访问及已生效入口的实际旁白名称已确认。可在开盖、单台 MG27U 经 Mac 自带 HDMI 直连、双屏非镜像配置下日常使用；其他硬件组合与长期稳定性不在本次结论中。逐场景证据类型、生命周期结果和剩余项见[本机验收矩阵](menu-bar-primary-acceptance.md)。

实际菜单已确认固定模式、已生效及恢复未完成状态，方向键能跳过信息项，回车能打开系统“显示器”设置，Esc 关闭已由用户确认。所有状态均提供文字；辅助功能检查器已退出，不要求用户在日常使用时开启。

可在**仅单活动内屏、非镜像**环境复现无外屏进程验收；脚本先检查条件，状态存入私有本地目录：


该脚本检查实际进程、目录锁、启动拒绝与责任保留；模拟事件和进程内菜单测试的结果分别记录，不替代外屏或桌面呈现验收。

## 外屏交接候选

候选菜单采用无勾选的单一外屏主动作：正常为“停用外接屏”，核验停用后原位改为“恢复外接屏”；进行中显示进度，不再同时显示重复恢复或再次停用项。真正恢复未完成时仍显示错误和唯一“重试恢复”，不能仅因画面亮起就显示成功。当前HDMI链路已有三轮Mac往返、正常退出重开及菜单动作的真实验证，独立核验恢复记录无pending。

2026-10-30已补PC手动使用和开盖后完整布局／责任结清证据。用户同意按当前这台显示器的手动停用／恢复收口，复用已通过结果，不再追加睡眠、持有中强退或换屏实验；这些场景的持续停用／自动恢复不作本次保证。输入检测未识别，当前连接的软件切源保持不可用。各日期结果与限定交付边界以[验证记录](external-display-verification.md)为准。

主动作暂称“停用外接屏”，正式名称待定；沿用当前显式启动方式，普通启动的模式列表仍不新增此项。限定交付不等于通用机型或完整异常矩阵准入；原生键盘接线、无障碍标签和禁用动作实现及离线核对保留，没有新增真实VoiceOver轮次，不将它记为实测通过。“显示器输入源”独立于主停用，未识别不影响单独停用。

候选保留原有“外屏主屏”和“仅外屏”入口。模式与输入设置按验收目录隔离，但内屏保护失败锁同时受原应用和当前目录约束，不能靠换目录解除；新失败也写入原应用保护锁。仅外屏入口重新可见不代表已解除原保护限制或完成其恢复验收，启动不会自动进入该模式。

交接期间改选受保护限制的仅外屏时，先处理已有外屏恢复责任，成功后仍拒绝停用内屏。恢复失败时仍可确认原连接并重试，菜单按实际恢复会话处理，不因所选模式改变而丢失入口；进度显示恢复外接屏，恢复后不会因这次模式切换擅自退出应用。

本次仅覆盖当前原屏通过HDMI直连原Mac端口的非镜像配置；动作前开盖、内屏可用，交接时保持应用运行。使用流程如下：

1. 选择“停用外接屏”，菜单先显示“正在停用外接屏…”。独立读回确认后显示“外接屏已停用，请切换显示器到 PC”，主动作变为“恢复外接屏”，不使用模式勾选；单独停用不探测或写入 DDC，也不会只切输入源而把 Mac 扩展桌面留在外屏。
2. 显示器可自行选择PC的有效DP信号；若未切换，再使用显示器可用的选源方式。Mac侧停用成功不代表已切输入或已出现PC画面；Mac内屏应保持可操作。
3. 在 Mac 内屏点击“恢复外接屏”，等待恢复确认，再手动切显示器到 Mac。原停用连接的 UUID 为零时，候选会要求确认当前是同一台原显示器、通过 HDMI 直连原 Mac 端口；同屏同口拔插后接回也可以，换屏、换口或不确定时取消。机器校验通过后确认仅这一次有效，取消不写配置；人工认错可能短暂向所接屏幕输出 Mac 画面。菜单核验恢复成功后显示“外接屏已恢复，请切换显示器到 Mac”，结束交接意图，不立即重新停用。无信号时不能选源的显示器，需要先恢复 Mac 输出再选源。
4. 再次交接须显式选择“停用外接屏”或点击重试。切换其他模式先结清原停用责任；处理中禁止并发模式切换和重复恢复。

当前连接已检测一次且未识别输入能力，无需为了本次收尾重复检测。软件仍保留按需查询与受限一次性选源实现，但不在本次交付保证中；未发送Set VCP，不开放自动偏好，也不将未识别推断为硬件不支持DDC。

“恢复未完成”或“恢复失败，尚未退出”会保留原责任和“重试恢复”。保持开盖、同一原屏通过 HDMI 直连原 Mac 端口，从显式恢复入口重试；换屏、换口或无法确定时取消该次连接确认，不以拔线、删除记录或强退作为正常完成。连接确认不代表确认新的恢复布局，启用后仍须核验真实身份和适用布局。正常退出需先确认 Mac 配置恢复，仅等待切回 Mac 输入不等于配置失败。详细恢复边界见[外屏恢复说明](external-display-recovery.md)。

实际外屏恢复会话尚待核验且已合盖时，菜单显示“恢复未完成，请开盖完成核验”，操作显示灰色的“开盖后重试恢复”。外屏亮起不代表完整双屏布局已核验；开盖后重新打开菜单即可刷新，再从恢复入口继续。提示不会清理责任，也不表示支持合盖停用外屏。

离线测试核对菜单文字、动作分派、忙碌禁用、模式入口及辅助功能名称字符串；已有画面和免拔线往返证据复用。真实VoiceOver交互及新合盖提示的现场覆盖限制保留，本次不再安排集中实机验收，不因范围收口删减无障碍实现。
