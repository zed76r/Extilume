# Design

## Context

见 [proposal](proposal.md)。现有 Core/Native 已有真实停用、独立保护、恢复记录和睡眠门禁。D2 睡前 C 人工确认正常，醒后外屏切分抖动；主控醒后 23 次完整 C 核验失败，主辅均无显式启用／停用／原点提交标记，辅助最终仅核验恢复。已绑定旧源码支持缺外屏的条件推断，仍不证明物理断开、系统隐式作用域回退或画面异常的因果。

`DisplayEnableTransaction` 对停用使用 `.forAppOnly`、恢复启用使用 `.forSession`；这只是待核对的事务所有权方向，私有 API 的实际作用域不能靠名称推断。当前不指定“加等待”或改某个配置选项为已证实修法。

## Goals / Non-Goals

**Goals:**
- 修复实际画面及可靠恢复，形成 App 可接入且可单独验证的恢复契约。
- 与 App 主体并行开发，保留最新 C、保护、预算和真实效果的全部边界。
- 以已有证据和最小反例先淘汰无效假设，再协调有限现场。

**Non-Goals:**
- 不重做菜单、模式偏好或打包，不管理其他应用窗口和 Spaces。
- 不自动注销、重置图形会话、强制断电或重放旧实验记录。
- 不通过放宽身份／来源、增加固定等待或将黑色覆盖当停用来取得通过。

## Decisions

### 1. 按职责拆分，不把“能开发”写成“能日用”

本提案负责恢复引擎、画面故障和完整恢复证据；[App提案](../archive/2026-10-25-add-internal-display-disable-mode/proposal.md)负责真实模式命令接入、菜单状态和构建。App 现在可实现和做离线集成，不等本提案全部通过；实际硬件开发验证须另有新候选、就绪保护与明确范围，发布仍以核心及 App 实测合格为前置。不会交付一个仅有灰色入口的主体，也不会把尚未准入的原型作为日常版替换运行中的 App。

本提案4.4另承接App原5.5的联合验收责任，来源是`add-internal-display-disable-mode`，与下表原验证的5.5区分。App账本仅保留迁出及未验证记录，主体按23项独立收尾；验收责任未完成前仍阻断日用发布。联合验收核对真实事件经原生会话／IPC到App的状态、动作门禁和生命周期结果，不以UI受控状态替代；不为迁移新增一套物理矩阵。

### 2. 先补齐可判别的现有证据，再选择修法

关联恢复前后屏幕角色、独立硬件状态、显式写入及事务作用域结束边界；已有日志不足的字段明确记缺口。用合成场景覆盖内屏缺失、外屏缺失、空集、完整 C、精确已知 B 与未知完整布局，但不把合成模型当作驱动效果。对具体假设保留可重复反例及修复后的定向检查；没有这些证据，不新开修复验收轮次。若现有证据不足以选择修法，可先按 2a 准备独立有界诊断，执行仍须另行授权。

仅将精确已知 B 重新挂责的旧修复不覆盖本轮子集；现有保守拒绝本身未被证明错误。若需要只读稳定化等待，须先证明具体缺失角色及来源，等待不能清故障、重置最早起点或授予新写权限，且不能宣称独立解决画面故障。

### 2a. Dg1 只建立正休眠的普通双屏 C 基线

**问题与判别边界。** 在诊断工具零新增停用、未观察到意外控制进程的条件下，普通双屏 C 经实测正休眠后是否仍出现异常？同时记录外屏是否活动、完整 C／原模式是否匹配以及人工实际画面，区分拓扑／模式变化与软件完整 C 下的物理异常。旧普通 C 对照人工正常，但证明的休眠下界为零，不能替代这项基线；D1 的历史正休眠区间也不能移入本轮。

这是被动基线，不原样重跑 D2，不测试新 C 确认后的重应用，不先选定私有事务选项作为修法。同 boot 历史停用、隐式重配及未捕获的进程干扰仍可能存在。异常结果最多反驳“本轮工具新增停用是必要条件”；没有全轮 owner 缺席证据时，不推论 owner 是否为必要条件。正常一轮不证明因果或修复。

**候选与就绪。** 候选是单独冻结的只读采集工具、witness、时钟工具及其源码／二进制摘要、参数白名单和单轮配额，不是新的仅外屏 App。任务 1.4 的静态工具准备及离线验证见[Dg1说明](../../../docs/internal-display-recovery-dg1.md)，不能据此认为完整 3.1／3.3 已冻结；[既有共享清单](../../../docs/internal-display-recovery-acceptance.md)仍是完整恢复验收的准备快照。本节定义独立诊断的准入边界，现场前必须具备：

- 核对当前 boot、系统／显示环境、工具绑定及 D1 校准适用性；只复用适用的源码／工具校准结论，不复用旧样本、电源区间、执行包消费标记或授权。
- 按原门槛核对日常会话和两份旧实验责任。未解决的责任冲突、保护／在途状态或来源不明均阻断现场；不自动重放、覆盖、删除记录或清除持久故障锁。必需的旧责任恢复不包含在 Dg1，须先有相应授权。
- 日常 App 已退出且记录不存在时，清单仅可显式声明默认 `~/Library/Application Support/Extilume/recovery-record.json` 缺失，同时绑定既存私有目录的 device／inode，`daily=null`。领取配额后及全轮记录检查中，以不跟随符号链接的目录描述符复核布局和 `internal-session` 记录均不存在；请求睡眠前再次强制复核。只有确切不存在才接受；目录缺失、替换、权限错误、链接、内部责任出现均停止，不创建目录或伪记录。自定义目录归属未核定则阻断，不把默认目录空置解释为所有会话无责任；旧两份仍须原件摘要与 restored／无未决责任核验。
- 若日常 App 仍运行，未来现场白名单可列最多一次正常退出，记录其既有 C 恢复补偿及实际进程退出；退出请求已发或短 argv 都不等于实际退出。已退出则不为测试先启动。正常退出不能直接得到要求的内屏主屏完整 C／原模式，或仍有控制／保护进程，则阻断，不临时改主屏、布局或模式凑条件。
- 睡前由独立读回核对两次完整 C、原模式及可信身份，并由用户确认双屏实际正常。诊断阶段不接管显示控制责任，不启动新 owner／helper；正常退出补偿单列，不能把它报告为全批次零显示写入。
- 现场授权前明确异常收尾操作者、允许的安全恢复动作与交接方式；未落实则不开始。采集工具没有默认的布局恢复、强退、重启或物理救援权限，不要求用户为保留观测而维持异常画面。

**动作与截止上限。** 独占消费本轮额度，任何动作请求前先记账；崩溃、前检失败或未真正入睡都不重置。仅准备下列一个诊断分支，不并入 F／S 故障矩阵：

| 动作 | Dg1 上限 |
| --- | --- |
| 诊断批次启动 | 1 次；失败不重试、不自动补轮 |
| 已运行日常 App 的正常退出 | 最多 1 次，须单列授权；不得强退或先启动再退出 |
| 普通睡眠请求 | 最多 1 次；未入睡也视为已消费 |
| 新控制会话／停用／重应用 | 0 |
| 诊断阶段额外显示提交、主屏／布局／模式改写 | 0 |
| 故障注入、拔线、输入源切换、重启日常 App | 0；异常救援仅按事先明确的交接范围执行并保留失败 |

从消费本轮额度、进入首项现场准备动作起，总窗口最多 180 秒连续时钟，包含实际睡眠。采集截止取该绝对期限与首次适用唤醒边界后 10 秒连续时间的较早者；睡眠跨越总期限不获得额外十秒。不为截止强制唤醒、杀保护或清责，醒后只做已授权安全收尾，不继续诊断或再次睡眠。两个期限都是停止收集的上限，不是固定亮屏等待、恢复通过期限或新写入授权。

**证据与停止线。** 复用已有事件观察和有限独立读回，不新增高频轮询、自动桌面截图或高权限进程审计。睡前／醒后各至多两次独立完整状态读回，关联本轮时钟样本、唯一合法电源配对及正休眠下界；记录匿名内／外屏角色、活动集合和 C／模式匹配谓词。软件正常与用户实际画面分列；人工异常标记只是观测时刻，不能冒充实际故障起点。

进程归属观察覆盖全轮，并声明机制能力与盲区；仅前后两次进程列表不证明全轮零 owner。监测不能证明完整缺席时，owner 因果结论必须未知，不把有限观察升级为不存在任何停用或控制写入。实际观察到意外控制进程或出现承诺范围内的观察断档即停止，不杀掉后继续。出现画面异常、救援、身份／C／模式不一致、关键端点缺失、配对不合法、无正休眠下界或超时，同样停止新动作；不为补数据延迟安全交接。

结果分别报告「诊断信息是否充分」「实际画面及救援情况」「哪些假设仍未知」。未证明实际休眠或缺证记证据不足，不能仅据此报画面故障；已观察到异常或救援则保留失败，即使后来 C 读回正常。Dg1 不计作 1.3、4.1–4.4、故障十秒或任何 F／S 分支通过，不抵消历史失败或三次义务；无异常也不自动开放下一轮。新诊断问题或主动控制分支必须另行修订范围、候选、总量及授权。

### 2b. 旧布局责任仅记录结清方案

只读前检显示两份旧实验记录仍为布局责任未决，当前完整 C 与其旧 baseline／applied 均不同；实际画面正常不授权采用新基准。现有 `recoverOnly()` 常规分支仍可能提交 `.forSession`，不能用确认 C 后调用恢复命令来声称零显示写入。

按[结清方案](../../../docs/internal-display-recovery-closeout.md)先设计专用记录路径：另获对具体两份记录、新 C 及限定备份／存储文件写入的明确授权，核验归属、独占所有权、原件及两次独立完整 C，保存不可覆盖原件后，仅在内存副本上采用新 C、完成 restored 转换和校验，再逐份一次原子保存与独立终验。无启用责任且来源已决才适用；禁止显示 writer、现有恢复、finalize／clear 入口。转换失败不保存，部分成功保留原件与回执、停止不补轮；历史失败、No-Go、锁及额度保持。

2026-11-03 已实现专用 `--closeout-layout-records --allow-record-write` 路径并做合成验证。Core 转换不持有显示 API，双方资格及原件先统一核对，实际原子替换前检查当前目录身份、原件与截止；替换后的同步失败保留不确定结果及旧 inode，不回写原件，普通 save 的失败回滚行为保持。保存后保存实际字节及前后摘要，最终复核两份内容。30秒窗口及三秒观察间隙在查询和回执写入返回后重新核验；系统调用不可抢占，停止不意味着尚未写入。完成文件须与退出0、无停止回执及独立终验合并判断。

专用候选及初始未授权模板见结清说明。后续新只读前检和一次日常正常恢复退出已完成；另获明确采用新C及仅记录结清授权后，专用候选单次执行失败，双方真实原件未变。消费及停止标记保留，禁止复用或重试；先离线定位停止原因，再决定是否准备新候选。两份真正结清前 1.5／4.3 继续阻断，不增加或勾选完成项。

2026-11-06 离线续行确认旧回执不能还原具体失败分支；保留旧绑定的完整源码字节后，仅为新工具补充固定阶段及脱敏错误类别，不修改旧回执或重试。嵌套检查成功恢复调用方阶段，失败保留停止阶段；不保存异常原文。保存阶段仍可能包含替换后同步失败，字段不能证明未落盘；停止回执自身持久化失败也不能保证阶段留存。新构建及合成反例不开放旧候选或 Dg1，执行／保存／期限门槛保持。

后续新候选及一次只读前检另获授权后完成，随后用户明确授权其单次仅记录结清。该执行退出1，在processes／closeout-environment停止：old-1已独立核验restored且基准为获准C，old-2仍owned／布局pending、原件未变；双方原件及回执保留，软件及人工收尾画面正常。没有重试、回滚或睡眠，Dg1仍阻断。后续先离线细分该门槛，再为剩余单份责任重新核定方案；现有入口要求双方owned，不能重纳已restored第一份或放宽资格补跑。

### 2c. 部分完成后仅处理剩余单份责任

本节只规划，尚未实现或授权执行。先将进程查询三个拒绝分支细分并完成纯合成验证，不放宽现有扫描规则；历史回执仍不足以定位具体系统调用。新只读诊断须覆盖生产扫描与自身 witness 回复／退出交错，不能借再次写记录触发诊断；错误或观察缺口继续阻断。

单份方案见[结清说明](../../../docs/internal-display-recovery-closeout.md#单份剩余责任方案仅规划尚未实现)。仅 old-2 为可写目标，old-1 及前次部分执行材料为只读凭证。新范围 `legacy-layout-residual-closeout-v1` 必须核对前次输入／消费／停止、双方 original、old-1 保存后摘要与独立终验，保持旧标记；旧双份入口不改成任意数量。只读凭证不进入可写存储集合，提交前后确认其字节、目录身份及 restored／无 pending 状态，不转换、保存或清除。

目标仅在独占、原件／会话／代次及 Core 资格匹配时，先持久保存新原件，再内存转换及一次原子替换。新 C、模式、同 boot 硬件身份和人工观察须重新取得；布局／模式须与前次获准 C 相符，旧数值 ID／boot 不代替新读回。任何变化先停止并重新核定，不顺带修改凭证。现有截止、同步失败留不确定结果、实际字节摘要及独立终验合同保持。新工具及合成反例就绪后，候选、具体清单及写入另获授权；不复用已消费尝试或 Dg1 额度。该准备属于 1.5／4.3 的前置责任，不增加或勾选完成项。

### 3. 复用现有安全机制并保持单一恢复归属

保留同用户 IPC、会话／代次、原子记录、独立身份读回、内屏启用位与布局分责。电源门禁在控制与辅助中独立生效，异步超时不假定原生调用已取消；所有写入仍须真实结果与独立核验。严格信息和受控在途重建规则从[归档合同](../archive/2026-10-24-validate-local-display-control/specs/local-display-verification/spec.md)继承，不以拆分削弱。

完整App已实测从内屏主屏直接停用成功，但恢复启用内屏期间的IOKit负向通知仍按原合同锁存故障并取消首次退出；原C与helper终验成功不能抹除该故障。App的修复采用同一退出请求内至多一次独立只读终验：原主辅均真实退出、干净IPC、精确恢复记录及独立凭证完整、故障同步持久保留后才准入；核验在原10秒绝对截止时间内完成，失败留责任。该流程不扩大disable Complete例外到恢复或scope=other候选，不解决或改判历史睡眠画面失败。

### 4. 一份共享覆盖清单

| 原任务 | 本提案责任 | App责任 |
| --- | --- | --- |
| 5.3 | 修复醒后画面／C恢复，验证核心睡眠与退出分支 | 验证真实菜单路径、模式切回和退出接线 |
| 5.4 | 主进程在各阶段失效的单一接管与十秒证据 | 提供可定位的App阶段及进程边界 |
| 5.5 | 拔线、辅助失效、在途及睡眠边界与检测盲区 | 同一候选下验证App事件和故障呈现 |
| 5.14 | 信息／负向兼容、最早起点及同轮计时工具 | 消费同一份证据，不另跑一套矩阵 |

原归档四项不改判、不补勾；新任务从零建立修复责任。完整验收前冻结实际分支和复用依据，历史九个通过子轮按影响决定适用性；关键故障仍至少三次。辅助进程资源与清理也在同一清单：记录完整App下内存、CPU、唤醒频率的数值／单位／观测时长，核对正常退出、模式切回和异常恢复三类收尾；仍有责任时不清理保护。D1 已通过计时门，在时钟、环境和工具绑定仍适用时复用，不机械再校准。

## Risks / Trade-offs

- 画面可能涉及私有事务或驱动，离线模型不能证明根因 → 明确证据边界，只为有判别力的候选协调现场，不承诺固定轮数能修好。
- App接入后出现新生命周期路径 → 核心证据和接线证据分列，冻结同一实际构建后共享验收。
- 功能实现被误认为日常发布 → 开发构建独立路径与明确未准入标识，不覆盖现有已验收App；发布门槛保持。
- 旧实验记录仍有布局责任 → 继续隔离保留，不自动清理或恢复。

先完成已有证据的离线归因；缺少修复依据时，可先完成 1.4 的 Dg1 诊断工具与离线停止线验证，再在另获现场授权后执行 1.5。诊断结论不足则 1.3 继续阻断；形成具体原因后才实现修复候选、完成共享验收冻结及第 4 组真实验收，不由诊断自动转入主动控制。

开发构建与日常安装、状态目录隔离；实际启动或切换硬件前另行明确交接范围。新候选仍须先恢复旧责任并核对适用性，不能删除记录绕过门禁；本次规划修订不授权该恢复，未解决的责任冲突不放行现场。现场失败停止候选、保留原证据和安全恢复责任；不为完成本提案修改历史 No-Go。
