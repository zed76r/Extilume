# Proposal

## Why

用户要开盖真正停用内屏、只用外屏。当前原型已证明基础停用有效，但恢复双屏后再睡眠唤醒仍出现外屏切分抖动并需人工救援；不能把状态机或计时自检通过当作画面故障已修复。将恢复可靠性独立攻关，使完整 App 与真实模式接入可以并行实现，同时保留日用准入门槛。

## What Changes

- 建立独立的 `internal-display-recovery` 契约，承接原验证 5.3、5.4、5.5、5.14 的技术修复与恢复证据责任；原验证的 No-Go 归档、失败、未验项及已耗额度均保留。
- 从已保存 D2 证据区分主控、辅助及系统事务作用域：醒后两进程均没有显式停用、启用或原点提交标记，主控出现 23 次完整 C 核验失败；尚不能据此判定隐式作用域回退、缺失屏幕角色或图形故障因果。
- 先形成具体可证伪的修复假设、反例与候选，再验证真实输出。单纯加超时、放宽子集布局或挂责不能作为画面修复；不预先指定未经证实的修法。
- 复用同用户独立保护、最新用户 C、单一恢复归属、电源写门禁及十秒清醒预算，补齐睡眠／退出／故障交错的可靠恢复。
- 将真实物理故障检测、主辅失效和恢复计时集中为一份有限共享清单；与 App 集成共用冻结候选证据，历史适用证据按影响复用，不先后重跑两套完整矩阵。
- 以任务4.4完整承接`add-internal-display-disable-mode`原5.5的App联合验收，保持未验证；核对真实异常状态传递、未准入保护及App／所有者／辅助生命周期结果。App主体可按其余23项独立收尾，发布仍须本项及恢复必需证据合格。
- **BREAKING**：将 App 开发准入与日用发布准入分开。`add-internal-display-disable-mode` 可先实现双模式、真正停用／切回／退出和打包；本提案未通过前，开发成果不得被宣布为已验收日用版，也不得自动替换当前外屏主屏版本。
- 本规划不授权新睡眠、停用、拔线或故障注入；新现场须有修复依据、明确候选及单独授权。

## Capabilities

### New Capabilities

- `internal-display-recovery`：内屏启用位、最新布局 C、睡眠与全过程故障下的独立恢复、物理效果及计时证据。

### Modified Capabilities

无。现有 `primary-display-session` 的日常主屏契约保持；App 菜单与交互由 `internal-display-session` 提案承接。

## Impact

- 涉及 `ExtilumeCore` 的恢复责任及计时、`ExtilumeNative` 的受保护事务、主辅进程与电源生命周期，以及相应测试和受限采集工具。
- 当前候选仍为失败；App 真实仅外屏接入是另一个并行交付，不以灰色占位入口代替，也不以可构建代替物理验证。
- 两份未结清实验布局记录保持隔离，不回放、覆盖或删除；既有日常 App 和 `openspec/specs/` 本轮不变。
- 依据见 [No-Go 原验证](../archive/2026-10-24-validate-local-display-control/proposal.md) 与 [失败／责任记录](../../../docs/local-display-verification.md#d2-首会话失败并停止2026-10-24)。
