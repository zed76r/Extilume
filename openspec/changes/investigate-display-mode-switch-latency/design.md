# Design

## Context

动机见 [proposal.md](proposal.md)。以下是当前工作区静态事实，尚未运行应用或测量硬件；工作区已有无关诊断改动，实施前须记录实际构建来源和差异。

- `MenuBarApplication.selectMode` 先渲染 applying 再调用协调器。`DisplayModeCoordinator.selectMode` 区分首次启动、同模式重试、无操作和 `finishHandoff`；互切须等旧控制器退出恢复、清理责任后才启动下一控制器。勾号／偏好变化不等于主屏已经改变。
- `PrimaryController` 默认用 `freshSnapshot`：独立 witness 进程执行 `stableSnapshot`，每轮比较前等待 100ms，最多 20 轮；每次 `readSnapshot` 都读取显示列表及 registry 身份证据。`apply` 包括初始快照、持久化后的写前独立读回、原点提交及写后目标读回；上层还有状态核验。多次进程启动和探测是候选成本，不是已证实根因。
- `PrimaryReapplicationScheduler` 有 1 秒事件合并，但首次 `startApplication` 直接推进 `performApplication`；不能把重连／唤醒定时器直接认作菜单点击延迟。
- 仅外屏经 `InternalApplicationController` 启动 worker、身份握手，再由 `GuardSession`（`DisplayGuard.swift`）准备保护 helper。`translateProtectedInternalLayout` 在主屏提交前读快照及多次执行 gate；`configureOrigins` 在开始和提交前均调用 gate。`freshGuardSnapshot` 包含独立显示快照及内屏硬件 witness，可能放大累计耗时，但每次验证均有现存安全用途。
- IPC 超时和 witness 退出轮询是上限／提前完成条件；`InternalApplicationController` 的 10 秒退出 watchdog 不在首次应用路径，不能将这些数值简单相加当作实测延迟。
- 当前源码保留 `internalFailureLatched` 拒绝仅外屏的逻辑。本次未读取实际偏好或恢复记录，不能断言当前运行实例可否切换；拒绝请求须单独分类。

## Goals / Non-Goals

**Goals:** 找出点击后、实际主屏改变前的主导耗时；做有证据支持的最小修复尝试；在原保护契约下验证真实体验变化。

**Non-Goals:** 不重构恢复架构，不合并独立 witness 与控制进程，不直接删除 gate 或用旧缓存代替新鲜核验，不改变 `.forAppOnly` 作用域，不延长恢复预算，不迁移偏好／恢复文件。恢复专项的剩余实机验收保持原归属。

## Decisions

### 1. 先建立同一请求的分段时间线

复用现有单调时钟及生命周期诊断方式，最少记录：菜单动作进入、协调器受理／拒绝、执行队列开始、旧模式恢复结束、worker／helper／witness 启动及返回、保护就绪、主屏提交开始／返回、实际主屏读回、内屏停用读回、状态发布／渲染。用本轮临时关联标识串联跨进程记录，保留总耗时，不扣排队或恢复时间；记录阶段、耗时和结果即可，不输出显示器序列号、完整身份或原始敏感记录。

程序动作进入不能代替物理点击时刻。现场用同一观察方法记录点击与可见桌面变化，并注明帧率／观察误差；系统设置只采集可比较的端到端效果，不推断其私有实现。诊断开销应单独估计，不能因加日志制造基线差异。

备选仅计 `CGCompleteDisplayConfiguration` 会漏掉本问题最可能涉及的提交前等待，因此不采用；不新建通用遥测框架或长期服务。

### 2. 根据耗时证据选择最小修改

先分别归因到主线程／串行队列排队、探测／进程启动、旧模式恢复、保护握手、原生提交和状态刷新。若重复静态元数据获取占主要成本，只考虑在身份及生命周期边界严格失效的范围内减少该成本；若排队或等待占主导，只调整被证明无安全用途的调度；若原生提交占主导，记录系统边界并验证现有调用方式，不盲换私有 API。

每个候选都要写清假设、预期减少的阶段和可证伪条件；保留所有写前新鲜状态、身份、代次、独立保护和持久化约束。不能因调用次数多就删除核验，不能一次改多个机制而失去因果对照。若没有安全且有效的候选，交付调查结论，修复／性能验收任务保持未完成。

### 3. 分场景比较，不混淆主屏迁移和完整停用

固定 Mac、macOS、显示器、连接方式、缩放、刷新率、拓扑和起始 C；记录应用版本、源码 SHA、未提交差异及首次／后续请求。场景为：内屏主屏直接选择外屏主屏、确认手动布局后的显式重试、内屏主屏直接选择仅外屏、外屏主屏→仅外屏、仅外屏→外屏主屏。已为目标的无操作单列，不能算作快速切换。

获准现场试验前冻结候选、具体场景、次数、误差和停止条件。普通主屏对照建议每组 5 次，保留逐次值、中位数及最大值；仅外屏批次与恢复专项协调并单独获准，不因本设计默认执行。每次起始布局恢复也属于显示写入范围，不能悄悄从失败状态继续下一轮。

候选被判为“有提速”需目标场景点击至可见主屏变化的中位数下降超过测量误差、最大值无超出误差的退化，且无新增错误或恢复失败。仍明显慢于系统设置时报告差值，不能只说“已解决”。少量样本不报告伪精确 P95；未复现、样本不足或差异落在误差内均为不确定。此调查不预设未经实测的零延迟／固定毫秒承诺。

### 4. 离线时序与物理效果分别验收

复用 `PrimaryApplicationTests`、`PrimaryStartupTests`、`DisplayModeCoordinatorTests`、`PrimaryReapplicationSchedulerTests`、`ProtectedInternalApplicationTests`、`InternalApplicationControllerTests` 及 `SnapshotWitnessTests` 的注入点。只为实际修改补充小型回归：显式请求与自动事件合并的区别、旧代次取消、重复点击不并发、写前变化拒绝、保护先于写入、互切保留 C、成功状态晚于读回。测试以调用顺序／可控等待为主，不用脆弱的真实秒表断言替代实机测量。

## Risks / Trade-offs

- [减少等待可能使用过期状态或跳过保护] → 每个候选证明保留核验边界，相关负向测试失败即撤回候选。
- [减少进程启动改变 witness 独立性] → 优先减少无关准备工作；任何改变独立证明语义的方案超出本最小修复范围，需另行评估。
- [系统设置和应用承担不同恢复义务] → 主屏实际变化可对比，完整仅外屏流程单独报告必要成本。
- [现场出现黑屏、冻结、故障锁或未决恢复] → 停止该批次，保留保护和责任；不清锁重试，不将人工救援算成功。
- [未提交诊断改变基线或共享路径影响第三模式] → 固定候选来源，检查共享调用者；必要时运行相关离线回归，不扩展到 PC 输入／停用外屏现场试验。

## Migration Plan

只新增诊断和有依据的局部修复，不迁移持久化数据。离线通过后再对获准的明确候选做现场对照；安装、替换日常应用、commit／push 均按独立授权执行。若候选无收益或回归，撤销本候选代码，保留脱敏调查结论和既有恢复责任，不以清记录作为回滚手段。

## Open Questions

- 用户感知的长等待主要出现在首次请求、同模式重试还是互切？各路径分别采样，不预先归为同一个原因。
- witness 创建、身份探测、旧模式恢复、保护准备和原生提交各占多少时间？由首轮分段数据回答。
- 相同条件下系统设置的实际耗时及计时误差是多少？现场对照后记录，不把“瞬间”转写为零。
