# Design

## Context

动机与范围见 [proposal.md](proposal.md)，行为见 [spec.md](specs/primary-display-session/spec.md)。本阶段依赖 [阶段零](../validate-local-display-control/design.md) 的主屏路径本机通过，包括应用退出后恢复 C 的最终读回；规划存在或原型编译成功都不满足依赖。内屏停用未通过不阻断此阶段。

当前没有应用目标。这里将已验证的原生控制与恢复代码放进最小菜单栏应用，不重新引入另一套显示工具。公开 [显示重配置回调](https://developer.apple.com/documentation/coregraphics/cgdisplayreconfigurationcallback) 可来自本应用、其他应用或硬件变化，因此不能把所有回调都当作自动重新应用命令。

## Goals / Non-Goals

**Goals:**

- 用一个菜单入口表达模式意图、实测状态与恢复责任，允许用户理解失败并重试。
- 将启动、热插拔、唤醒及退出接到同一套已验证的串行事务和恢复记录。
- 正常退出与重新运行均先处理未决责任，避免运行次数改变恢复目标。

**Non-Goals:**

- 不加入仅外屏占位入口、设置窗口、快捷键、暂停开关、开机启动或第三方依赖。
- 不扩展分辨率和窗口管理，也不为尚未实现的多屏建立策略系统。

## Decisions

1. **使用原生 AppKit 菜单栏应用。** 一个应用目标，以 `LSUIElement` 配置菜单栏生命周期，采用 `NSStatusItem` 与原生菜单；主线程负责菜单呈现，串行工作队列负责显示控制。相比 Web 容器或完整 SwiftUI 设置界面，这个界面所需代码更少，且退出前恢复可由应用生命周期直接协调。只复用阶段零实际需要的控制、观测和记录代码，不创建新的框架层。

2. **模式意图与实际状态分别保存。** 本阶段唯一意图为外屏主屏，无需首启选择或写入双模式偏好；下一阶段再增加选择。状态根据读回更新，菜单文本和可行动作如下：

   | 状态 | 呈现 | 动作 |
   | --- | --- | --- |
   | 缺少外屏 | 等待外屏连接 | 退出并恢复 |
   | 控制进行中 | 正在应用外屏主屏… | 暂停重试，允许进入退出恢复 |
   | 读回成功 | 外屏主屏已生效 | 退出并恢复 |
   | 用户主动修改 | 当前使用手动配置 | 退出并恢复 |
   | 不支持 | 暂不支持：具体原因 | 打开显示设置、退出并恢复 |
   | 控制失败且回滚成功 | 应用失败，已恢复 | 重试、退出并恢复 |
   | 责任未解决 | 恢复未完成／无法确认显示状态 | 重试恢复 |
   | 退出恢复中或失败 | 正在恢复并退出…／恢复失败，尚未退出 | 失败时重试恢复 |

   不支持原因区分镜像、多外屏、虚拟屏或物理身份无法确认。即使当前拓扑不支持，未决恢复状态仍须呈现。状态不能仅靠图标颜色表达，菜单提供文字和可访问名称。控制期间不发起并行重试。

3. **只有生命周期事件触发重新接管。** 启动先检查未决记录，然后观测拓扑；连接、重连和唤醒合并为一次稳定后的应用。普通配置变化只更新实测状态与用户候选基准，不立即抢回。断开后停止接管并处理当前可恢复部分；外屏回来时先确认身份与历史责任，再判断能否重新应用。一个事务结束并读回前，不执行下一轮事务；已满足目标也不反复写入。

4. **沿用阶段零的恢复责任模型。** 接管前记录最新真实用户配置，主屏及原点作为一致布局组恢复。应用只改变主屏与布局，保留用户分辨率等其他设置。自发回调、未撤销的 B、模式内重试都不能更新基准。来源不明时不猜测 C，不继续接管；保留责任并呈现无法确认状态。恢复记录受当前用户权限保护，使用本机已验证的身份匹配，不在日志输出标识符。

   常规主屏控制使用已验证的 `.forAppOnly` 事务，显式恢复使用阶段零验证过的补偿及提交作用域。不把 `.forAppOnly` 描述成精确快照恢复，不调用永久配置重置来冒充 C。退出后的最终效果、外屏缺失后再连接的残留效果，都必须在本阶段完整应用验收中复测。

5. **退出是恢复事务。** 点击“退出并恢复”后冻结新接管，等待或撤销当前控制并恢复适用配置。确认恢复成功后清理本次责任和事件订阅，再退出；仅控制 API 返回成功不能进入完成状态。缺失外屏不强制重建；已撤销的部分可结清，无法证明消除的责任保留。恢复失败取消正常退出并显示重试入口。强退无法依赖该入口，主屏路径的作用域回退行为在阶段零及本阶段故障验证中单独确认。

6. **限定硬件支持，并在运行时确认。** 使用阶段零已验收的当前 Mac、物理外屏身份与连接方式，运行时核对非镜像、恰好一台目标外屏、桌面可用且状态稳定。列表计数不是物理性质证明。条件不符只显示原因，不自动解除镜像，也不自动选择额外显示器。环境变化不能直接沿用旧准入结论。

## Risks / Trade-offs

- 系统退出回退或用户修改导致恢复结果偏离 C → 复用已验收路径，完整应用退出后再次读回；不通过时阻断交付。
- 事件密集或用户修改与事务交错导致基准污染 → 单一队列与事务阶段区分，针对交错事件验证，疑义时保留责任并停止接管。
- 外屏缺失使布局不完整 → 仅处理当前适用部分，保留未决责任，不将暂时的单屏状态认作旧配置已全部恢复。
- 恢复失败使正常退出延后 → 显式呈现尚未退出并提供重试，避免隐藏未解决状态。
- 仓库只有规划，硬件兼容性仍未证明 → 实现以阶段零运行证据为前置，不以本次文档验证推断应用可用。

## Migration Plan

无既有用户数据需要迁移。先确认阶段零主屏证据有效，再建立应用目标并接入已验证代码。完成本机连接、唤醒、用户 C 与退出验收后，阶段一才可日常使用。撤回阶段一时先运行恢复流程并确认结果，再移除本任务构建的应用；未决记录不能随着撤回被删除。

阶段二增加模式选择和保护进程时沿用此能力的自动应用、配置来源与退出契约；第一版不提前持久化用户从未选择过的双模式偏好。
