# Design

## Context

见 [proposal](proposal.md)。现有 AppKit 菜单栏程序已经提供外屏主屏、状态、手动C确认、恢复退出及构建；固定模式行没有选择动作，尚无模式偏好。受保护内屏停用在原生探测入口已具备基本效果，但尚未作为 App 会话接入，睡眠可靠性仍失败。

本次按用户最新要求拆分：本提案恢复主体与真正仅外屏的开发，底层恢复由 [fix-internal-display-recovery](../../fix-internal-display-recovery/proposal.md) 独立推进。先前阶段零 No-Go 和34/38账本不改判；本提案的任务按当前实现证据推进，不能把拆分规划或编译写成物理验收。

## Goals / Non-Goals

**Goals:**
- 在现有 App 上交付实际模式选择、真正停用、切回和恢复退出的完整接线。
- 保持用户选择、实际效果、保护和未决恢复分离，既有主屏行为不退化。
- 允许实现、替身集成及隔离开发构建先进行，真实仅外屏仍须受保护后端与物理效果验收。

**Non-Goals:**
- 不以灰色占位、黑色窗口或亮度控制冒充真正仅外屏完成。
- 不在本提案重写显示驱动或另建完整故障矩阵，不自动恢复旧实验记录。
- 不安装系统守护服务，不自动覆盖日常程序或将开发构建当成已准入日用版。

## Decisions

### 1. 将开发准入与日用准入分开

| 交付 | 本提案当前可推进 | 完成所需证据 |
| --- | --- | --- |
| 主体与接入实现 | 现在可实现菜单、偏好、模式协调、真实后端与辅助入口、打包 | 代码、状态／协议／迁移回归、可构建独立开发产物；不允许仅stub或不可用按钮冒充 |
| 真实仅外屏与App接线 | 有新候选和明确范围后协调开发验证 | 实际内屏退出桌面、外屏可用、切回／退出C及原模式；现场单独授权 |
| 日用发布 | 当前仍阻断 | 恢复提案合格及本App全部必需接线／效果验收通过 |

本提案不再以恢复提案“全部完成”为菜单及后端接入代码的实施前置。开发构建不是日常替换；未取得真实效果证据时明确报告缺口，不把第一行完成当成整项功能已合格。

### 2. 复用现有菜单和控制器，增加最小模式协调

保留系统菜单及可访问文字，增加互斥模式动作。协调器只序列化主屏与受保护内屏会话的启动、恢复、切换、停止，不再实现一套底层控制。现有主屏控制器继续服务外屏主屏；将原探测入口的受保护会话抽为可调用接口，命令行与 App 复用同一路径，不能用脚本stdin驱动当成正式产品接口。

原有会话在独立所有者进程中运行，同一 App 二进制提供固定私有会话／保护／witness 入口，类型化 framed IPC 不读 stdin；保留辅助在真实所有者退出后的终验。菜单进程持全局和根目录独占租约，主屏复用同一根锁，内屏使用受限子目录。异常恢复保留记录及持久门禁，正常切回前完成独立终验后才收束。

仅外屏动作须到达真实启用位事务与独立保护，实际效果读回后才呈现生效；替身只用于验证命令、失败和交错，不替代真实引擎。恢复失败保留可行动入口及未决责任，禁止并发重试或切换。

### 3. 意图、效果、保护与首选分别存储

偏好仅保存用户明确选择的模式值，恢复记录继续负责身份、C及尚未恢复的改动。首次双模式版本及从固定主屏版本升级时，没有明确首选则等待用户选择；不得把旧固定模式推断成双模式选择。有效选择重启保留，损坏偏好回到待选，无外屏只保存意图，不修改显示。

菜单勾号表示实际生效而非保存意图：仅状态为已应用、实际状态所属模式匹配当前选择、不等待显式激活且没有恢复／确认／退出动作时勾选。等待、应用中、手动调整和故障均不勾选；意图保留在偏好和明确状态文字中。旧模式迟到状态不能勾选新的选择。

稳定日用版按已选模式及安全条件自动应用；未准入开发构建不因恢复偏好而自动发起真实内屏停用，开发验证需显式操作和约定范围。这样可以实现和验证真实入口，同时保持当前日常版本及用户现场控制。

### 4. 切换共享最新C，先结清旧模式再接管

主屏→仅外屏：保留已确认C，原子记录目标责任，确认独立辅助就绪后再控制。仅外屏→主屏：先启用内屏并恢复适用C，结清辅助责任后应用主屏；中间配置不成为C，主屏布局责任不能随辅助退出丢失。

内屏主屏的双屏扩展同样可以直接选择仅外屏。应用保存该完整布局为C，辅助先核验当前C及准确的外屏主屏平移目标；保护就绪后应用自行平移，再真正停用内屏。不要求用户预先手动切主屏，也不要求接管时目标已经生效。切回和退出仍恢复原C及显示模式，中间外屏主屏布局不成为新基准。

用户手动修改遵循现有明确确认规则，不立即抢回。未知来源、身份变化、保护失效或睡眠门禁不被模式按钮、偏好、重启或重试清除。退出撤销新控制、恢复当前适用C，失败取消正常退出，继续呈现责任。

退出过程中，若原受保护会话明确报告故障，协调器同步持久锁存成功，且原worker正常退出、通道干净排空、helper真实退出及原记录独立终验凭证均完备，允许同一退出请求追加一次独立只读终验。新worker接收精确原记录，在同一独占锁下核对后读取完整C与硬件；不调用通用恢复入口，不写显示、不清故障。新worker正常退出及父端再次独立终验后，才能收束同一记录并退出。

该阶段保留原会话／代次／C／硬件约束和原故障，使用独立run token隔离旧回调；沿用退出开始的10秒绝对单调截止时间，在阶段切换、异步证明返回、持久锁确认后及清记录前同步检查。协议／握手／通信错误、未知helper、缺失终止事件或凭证、worker异常退出，以及第二阶段任何故障均不进入或不完成自动收尾。取消、替代或超时后旧证明不能清记录；同一请求不再启动第三阶段。模式交接在终验后仍重查故障锁，不能重新停用内屏。

### 5. 固定辅助入口与独立开发产物

在同一构建中打包受保护辅助入口，验证同用户、会话、代次和IPC；不用管理员服务。构建脚本支持独立开发输出及受限独立状态目录，保留当前运行的 `dist/Extilume.app`。开发产物不会由构建步骤自动启动；实际交接另行明确，未决记录不删除或迁移来绕过锁和来源核验。

### 6. 恢复证据单独归属，App仍做接线验收

恢复提案负责原验证5.3／5.4／5.5／5.14的核心实现与物理故障证据，并以4.4承接本App原5.5的真实异常状态、未准入保护及生命周期联合验收。本提案其余5.*负责真实菜单路径、构建／辅助启动、模式切换、手动C及退出接线，可独立完成主体收尾；原5.5在App账本保留为“已迁出、未验证”，不勾为通过。共用同一实际候选的一份冻结清单，历史证据按影响复用；关键故障三次、实际可交互和十秒清醒上界不降低，不为拆分额外跑原型全矩阵。发布仍须恢复提案及迁入的App联合验收合格。

### 7. UI呈现与真实接线分层验收

5.1允许使用与冻结产品UI同源的隔离Release host验证全部菜单状态的实际呈现及UI命令映射。host绑定UI／Core源码、资源、工具链与构建配置，使用真实MenuBarApplicationDelegate和AppKit菜单，不复制渲染或动作守卫。只读或受控状态来源须明确标注；外部AX、菜单局部截图及真实键盘／AX输入须关联同一host和状态，对象断言不能代替实际展开。

覆盖除状态枚举外，还包括无选择、等待显式激活、双模式差异、恢复／确认／退出忙碌及相应动作权限。所有控制、退出、退出回复和打开设置依赖均注入记录器，不接真实显示引擎、不调用产品租约或协调器入口、不改用户偏好；当前用户使用会话保持运行。产品不增加调试入口。

host和产品的进程、Bundle、激活策略、状态栏及生命周期差异必须单列。同源popup不能证明产品状态栏入口或其按钮AX，计算属性不能冒充真实按钮AX；首次／偏好升级仍使用真实偏好路径，产品入口及既有功能证据须逐项核对源码适用性，不能由host替代。

受控状态只证明状态到达后的UI呈现和命令发出，不证明真实故障产生、IPC、恢复责任或恢复时限。5.2–5.4及其他行为门槛保持不变；原5.5的验收义务完整迁入恢复提案4.4，完成5.1或主体收尾不能使其变成通过，也不改判既有未验项。

## Risks / Trade-offs

- 真实后端接入仍可能复现睡眠画面故障 → 恢复提案单独修复；日用发布继续阻断，硬件开发验证仍须新依据与范围，不在本轮启动。
- UI完成掩盖无后端 → 明确测试实际路由和打包入口，保留单独物理效果验收；仅按钮或stub不能标记接入完成。
- 旧主屏与新模式竞争责任 → 单一协调、状态目录锁、模式切换先恢复；覆盖旧会话和迟到回调回归。
- 用户误认为可日用 → 开发构建清楚标识未准入，不自动替换既有版本；成功编译或模拟状态不作为发布证据。

## Migration Plan

先在独立输出完成主体、真实接口和模式偏好迁移测试；固定主屏版本保持可用。实际新版本启动须先正常交接原应用、独立核对责任与布局，不能并行控制同一桌面。恢复提案合格且完整App验收通过后，才另行授权替换或安装日用版本；失败保留记录及原版本，不能自动结束保护或清理旧实验责任。
