# Design

## Context

动机见 [proposal.md](proposal.md)，新增契约见 [spec.md](specs/internal-display-session/spec.md)。本阶段同时依赖阶段零内屏路径的本机通过及阶段一完整应用的运行验收；沿用 [主屏会话设计](../archive/2026-10-16-add-menu-bar-primary-display-mode/design.md) 的菜单入口、自动应用和最新 C 恢复规则。

真正停用依赖私有 `CGSConfigureDisplayEnabled`，不是公开 API 保证。已有项目报告私有启用位在强退后可能不随 `.forAppOnly` 回退，拔线也可能出现陈旧显示列表或无法启用内屏的状态，来源及边界见 [阶段零设计](../validate-local-display-control/design.md)。这些案例决定需要独立保护，但不能证明 macOS 27.0.1 已满足 10 秒恢复。

## Goals / Non-Goals

**Goals:**

- 在同一原生应用中增加一个模式和一个最小辅助进程，复用已验证控制代码与责任记录。
- 对停用前、中、后及退出期间的主进程故障保持恢复能力。
- 把所选模式、实际桌面状态、保护状态及未决责任分开，避免显示错误成功信息。

**Non-Goals:**

- 不增加系统级守护服务、管理员安装步骤、自动登录启动或图形会话重置。
- 不保证主辅进程同时被终止、系统整体卡死或未经验证的系统与硬件组合可恢复。
- 不引入通用跨进程框架、动态显示策略或多屏支持。

## Decisions

1. **首次双模式明确选择，之后只保存用户意图。** 菜单增加“外屏主屏”和“仅外屏（停用内屏）”两个互斥项。阶段一的固定模式不是用户双模式选择，升级时无明确记录仍等待首选。持久偏好只存模式值，不能把偏好值当作当前生效状态。无外屏或不支持时仍保留选择；失败不静默改选其他模式。控制事务中禁用模式切换，事务完成后再接受下一次选择，保持菜单及可访问文字与读回一致。

2. **停用事务先落实恢复责任。** 新停用必须从内屏可用、外屏物理身份与桌面已确认的状态开始；若内屏被其他程序停用且本应用没有责任记录，不直接接管该状态。顺序为：读取最新用户基准 → 原子写入带事务代次的恢复记录 → 启动或更新辅助进程并收到就绪确认 → 再次核对拓扑 → 以阶段零验证的私有调用停用 → 读回实际结果。记录、保护或身份验证失败均不执行停用；提交结果不明时立即进入恢复。

3. **主辅进程使用同一份受限记录和明确恢复归属。** 辅助进程随 app 打包，以当前用户独立启动，不依赖主进程析构或退出处理器。使用本地 IPC，验证对端属于当前用户、当前会话及当前事务；恢复记录限制当前用户访问，校验版本、完整性和身份匹配。每次基准变化或重新应用前更新记录并确认辅助进程已读取，防止它仍按 A 恢复而主程序已接管 C。

   一个时刻只有一个恢复执行者。主进程正常切换或退出时与辅助进程协调恢复；主进程死亡或 IPC 失效时辅助进程取得责任。会话标识与代次排除陈旧辅助进程，新应用启动先确认旧责任结清，不能覆盖旧记录并再次停用。辅助进程失效而主进程存活时，主进程立即恢复并锁定新停用；不悄悄重启保护后继续运行。

4. **成功停用后继续事件等待。** 辅助进程在整个停用期间保留父进程退出、IPC 和本机已验证物理设备事件监听。相比一次性的短期救援计时器，这能覆盖长时间运行后强退；相比常驻系统服务，只在当前用户的停用责任存在时运行。空闲不持续高频轮询，控制与恢复窗口才使用有限次数重读。父进程死亡不使辅助进程自动被清理；只有内屏与它负责的适用配置确认恢复后才退出。退出后再次核对恢复效果，防止辅助进程自身作用域回退抵消结果。

5. **先恢复可用桌面，再处理适用布局。** 拔线、主进程故障、切换失败或不支持拓扑出现时优先启用本应用停用的内屏，然后按当前目标身份与布局恢复责任做补偿。整个过程的截止时间由故障实际发生起算，包含检测、调度、调用和读回，不能把前段延迟排除。辅助进程基于硬件事件尽早发现断开，不只依赖可能陈旧的在线列表；具体信号及重试策略必须与阶段零实测一致。

   外屏缺失时不重建不存在的显示器；布局只恢复当前适用部分，未确认责任保留。恢复没有达到 10 秒门槛即作为验收失败，后续重试仍可用于恢复，但不能改写失败结论。禁止自动注销或重置 WindowServer 作为补救。保护进程不能在仍有责任时单纯因计时到期退出。

6. **跨模式共享用户基准，恢复步骤不生成新基准。** 从主屏切到仅外屏时保留既有 C；从仅外屏切到主屏时先启用内屏并恢复辅助进程负责的适用配置，再应用主屏，不把中间配置存为原状。确认辅助恢复责任结清且主屏模式已读回后，辅助进程退出；新的主屏布局恢复责任仍由主进程保留，不能随辅助进程退出清除。自己产生的启用、停用、布局回调及睡眠前恢复均标记为事务结果。真实用户变化仍按阶段一规则观察，不立即抢回；下一次重新接管前确认并保存最新 C。用户改动尚未被应用覆盖时不回写旧值。

7. **睡眠与异常后重启先恢复，后接管。** 睡眠前尝试恢复内屏；唤醒时先核对内屏、拓扑及保护状态，完成未决恢复再按偏好重新应用。不能仅因收到唤醒通知而假定桌面安全，睡眠通知也不能替代读回。睡眠和唤醒边界的失败须纳入本机试验，既有故障计时不能在唤醒时重置。

   保护失效或恢复超时后保留所选模式，同时持久记录禁止自动停用状态；新连接、唤醒或重新启动不能清除该故障。恢复确认成功后，用户显式重试且所有前置条件重新满足才可再次停用；用户可选择已验收的主屏模式。此状态用于防止故障后的循环停用，不增加单独的暂停功能。

8. **正常退出以确认恢复为终点。** 菜单继续使用“退出并恢复”，冻结新事务并恢复最新 C 及内屏启用位。失败取消正常退出，显示“恢复失败，尚未退出”，保留辅助进程和记录，允许重试恢复。强退主进程仍由辅助进程处理同一责任。全黑时菜单没有帮助，因此错误菜单、手动操作都不能替代自动恢复的硬门槛。

## Risks / Trade-offs

- 私有 API 或驱动导致零活动屏后无法启用 → 本机强退与拔线实验为硬前置，失败仅保留主屏版本，不能发布降级停用功能。
- 主辅进程竞争、旧记录或 PID 重用造成错误恢复 → 同用户 IPC、会话与代次、单一执行者及新运行先收束旧责任，测试进程重启交错。
- 用户修改与主进程强退相邻，辅助进程读取旧基准 → 控制前记录握手；恢复时读回并保留尚未被应用覆盖的用户配置，加入此交错场景验收。
- 系统睡眠通知不保证恢复能在挂起前完成 → 开盖实测普通睡眠与边界故障，不因回调出现而判通过，不重置异常计时。
- 全过程保护增加资源占用 → 复用阶段零的事件等待方案，完整 app 再测资源和唤醒次数，不预估未经测量的数字。
- 辅助进程与主进程同时终止超出保护模型 → 明确证据边界，不将单进程强退验收外推到任意系统故障。
- 未决责任无法核对导致退出延后 → 呈现可行动恢复状态，保留记录，不能在清理时删除责任。

## Migration Plan

先确认阶段零内屏与阶段一应用验收均通过，再扩展 app 并打包辅助进程。阶段一升级到双模式版本时等待首次明确选择，不将固定主屏模式伪装成已选择偏好。

完整应用再次执行开盖真实停用、跨模式 C 恢复、长时间停用后强退、拔线、睡眠唤醒、辅助进程故障及恢复后清理。关键故障场景至少重复三次，每次从实际故障到确认恢复均不超过 10 秒，才能交付模式二。任何门槛失败时先恢复并保留证据，阶段二不进入日常使用；撤回到阶段一前先结清停用责任，不直接替换运行中的 app 或删除辅助进程。
